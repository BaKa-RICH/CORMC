# 算法接入关键坑

## 一、文档目的

这份文档不是实现方案正文，而是 **OneStep 迁移进入 `ramp_merge_algorithm` 时必须反复检查的坑点清单**。

后续每推进一个阶段，都需要回来看这些问题是否已经被真正解决，而不是“代码先跑起来了，但底层语义已经偏了”。

当前结论先固定如下：

1. 这次做的是 **迁移**，不是给 `one_step_algorithm` 加运行时接口。
2. `D:\PycharmProjects\CORMC\cormc\one_step_algorithm` 现状不破坏，作为单次规划黄金基线保留。
3. 初期不动 `engine` 外壳，不急着做 SUMO Replay。
4. 第一目标是让 `ramp_merge_algorithm` 在连续长时间滚动 DT 框架里，先把 S07 数值层跑成和 OneStep 一样。

## 二、必须盯住的关键坑

## 1. 坐标系坑

### 问题

`one_step_algorithm` 的场景是局部纵向坐标，核心语义是：

- `x_m0 = 0`
- `x_targets` 都是相对 MV 当前时刻的位置

而 `ramp_merge_algorithm` 使用的是全局坐标：

- 例如控制区起点约在 `6650m`
- 合流参考点约在 `6950m`

如果直接把 OneStep 的 `x_targets` 当成全局坐标去算，会导致：

1. `D_i`
2. 候选合流点
3. `d_i`
4. `t_m / p_m`

全部语义错位。

### 迁移要求

每次触发某辆 MV 规划时，都要先做一层局部坐标映射：

```text
x_local = x_global - x_mv_current
```

然后把局部坐标送入复制版 OneStep 内核。

内核算出的结果再映射回全局坐标：

```text
x_global = x_local + x_mv_current
```

### 验收标准

- 同一个物理场景，只要整体纵向平移一个常数，OneStep 规划结果的相对数值不应变化。
- S07 在 `+6650m` 后，局部规划结果仍应与原始 S07 一致。

### 当前状态

## 2. 场景语义坑

### 问题

`one_step_algorithm` 的 S07 不是一个完整长时仿真场景，而是一个“当前时刻快照”：

- 一辆 MV
- 一组主线车辆纵向位置
- 默认参考匀速参数

而 `ramp_merge_algorithm` 需要的是：

- 全局几何位置
- 区域状态
- 连续步进
- 触发条件

如果不先明确“快照场景”和“滚动场景”的关系，后面验证会混乱。

### 迁移要求

要明确区分两类验证用途：

1. **规划对齐场景**
   只验证“这一帧触发规划时，选 gap 和数值结果是否等于 OneStep”。
2. **滚动对齐场景**
   验证“进入控制区触发规划后，连续步进时仍保持同一套规划语义和运动语义”。

### 验收标准

- 第一帧规划结果必须能和 OneStep 做一一对比。
- 后续滚动若不重新触发规划，不应凭空漂移到另一套算法逻辑。

### 当前状态

`待解决`

## 3. 算法顺序坑

### 问题

`ramp_merge_algorithm` 当前框架里已有一版流程顺序，但内部很多步骤是占位版，不可直接当真。

当前真正的算法顺序必须以 `one_step_algorithm` 为准，而不是以旧框架顺序为准。

尤其要注意以下误区：

1. 不能先选 gap 再补算合流点。
2. 不能把“预测合流点”做成和评分完全分离的后处理步骤。
3. 不能把控制区、合流区、执行合流这三种状态混成同一层逻辑。

### OneStep 应保持的主顺序

```text
build_gaps
-> reachability
-> cooperation
-> timing / merge point
-> score
-> select_best_gap
-> build_best_gap_trajectory
```

### 迁移要求

在 `ramp_merge_algorithm` 中：

1. 控制区选 gap 时，候选 gap 必须逐个完整走完 OneStep 内核。
2. `p_m` 必须是每个候选 gap 的评分内生结果。
3. 轨迹生成时机必须服从“先评分选 gap，再生成对应轨迹”。

### 验收标准

- 候选 gap 的中间量可逐项打印并与 OneStep 对比：
  `reachable / Delta / delta_f_star / delta_r_star / d_i / t_m / p_m / J`
- 不能出现“best gap 对了，但中间量是另一套算法算出来的”。

### 当前状态

`待解决`

## 4. 规划状态建模坑

### 问题

当前 `ramp_merge_algorithm` 的状态更接近：

- `current_plan_gap`
- `locked_gap`
- `planned_trajectory_id`

它还不够表达 OneStep 的真实规划结果，因为 OneStep 一次规划影响的不是一辆车，而是一个协同包：

1. MV
2. 目标 gap 前车
3. 目标 gap 后车

### 迁移要求

需要新增“协同计划 bundle”语义，至少要能表达：

1. 这个计划归属于哪辆 MV
2. 选中了哪个 gap
3. 哪些参与车辆会被这次计划接管运动
4. 每个参与车辆对应的纵向轨迹参数
5. MV 自己的横向执行状态

### 验收标准

- 不能只有 MV 有轨迹，前后协作车却仍按默认运动走。
- 不能只记 `gap_id`，却找不到本轮到底接管了哪些车辆。

### 当前状态

`待解决`

## 5. 运动接管坑

### 问题

当前 `ramp_merge_algorithm` 的默认运动很简化：

- 纵向基本是 `x_next = x + v * dt`
- 速度基本维持当前值
- 横向合流是简化推进

这和 OneStep 的“匀速参考线 + 五次轨迹偏移”不是一回事。

### 迁移要求

第一阶段应先实现：

1. **纵向完全向 OneStep 靠齐**
   对本轮计划参与车辆，按 OneStep 轨迹推进。
2. **横向分层处理**
   控制区阶段只做纵向协调，不做实际合流。
3. **合流执行单独处理**
   MV 进入 `merge_execution` 后，再叠加横向执行轨迹。

### 验收标准

- 参与协同的前后车，其纵向轨迹不能再走默认直线推进。
- 非参与车辆仍可先保留默认运动模型。
- 控制区内不得发生实际横向合流完成。

### 当前状态

`待解决`

## 6. HDV / 不可控车坑

### 问题

后续一定要接入 HDV，不可把当前“全先按 OneStep 匀速和规划轨迹来”写死成最终结构。

如果现在把“所有目标车都视为可控协作车”写进核心数据流，后面接 HDV 会很痛苦。

### 迁移要求

第一阶段虽然可以先让主线车按 OneStep 运动，但状态层必须保留：

1. 原始可控性
2. 本轮有效可控性
3. 不可控分支下的打分与轨迹语义

也就是说，当前就要支持：

- 前车不可控
- 后车不可控
- 两车都不可控

至少算法分支不能缺。

### 验收标准

- `GapScore()` 不能默认按“双车都可控”处理所有 gap。
- 后续接 HDV 时，不需要推翻状态结构，只需要补默认运动模型和分支参数。

### 当前状态

`待解决`

## 7. 多 MV 资源冲突坑

### 问题

当前 acceptance 里已经检查了：

- 同一帧是否有多个 MV 选中了同一个结构化 gap

但这还不够。

因为即使两个 MV 没选中“同一个 gap”，仍可能出现：

- 共享同一辆前车
- 共享同一辆后车
- 前一辆 MV 已经拿走某个协作车的调整能力，后一辆 MV 还继续假设它可满额协作

### 迁移要求

多 MV 阶段至少需要两层保护：

1. `selected_gaps`
   防止同一个 gap 被重复选中。
2. `reserved_vehicle_ids` 或等价机制
   防止同一协作边界车被重复占用。

更进一步时，需要考虑“前车已被前一辆 MV 规划部分调整后，后续 MV 看到的是更新后的局部 gap 几何”。

### 验收标准

- 不允许多个 MV 在同一规划轮次里同时接管同一辆协作车。
- 不允许后一辆 MV 仍按旧快照高估剩余协作空间。

### 当前状态

`待解决`

## 8. 触发与稳定性坑

### 问题

文档已经明确：

如果本步没有触发规划：

```text
trigger_plan == False
```

那么就不应：

1. 重新识别 gap
2. 重新打分
3. 重新生成规划

否则会出现每 `0.1s` 漂移一次目标 gap 的问题。

### 迁移要求

要严格区分：

1. **规划触发帧**
2. **轨迹执行帧**

非触发帧只能：

- 继续执行已有计划
- 或走默认运动模型

### 验收标准

- 同一个计划周期内，如果没有新触发，`current_plan_gap` 不应无故变化。
- 轨迹执行过程中不能偷偷重算 OneStep 结果。

## 9. 验证口径坑

### 问题

如果一开始不把“到底算通过什么”定义清楚，后续很容易出现：

- best gap 看起来一样
- 但中间量不一致
- 或者第一帧一致，滚动 30 帧后已经偏掉

### 迁移要求

S07 阶段至少固定三层验证：

1. **规划数值验证**
   对比 `best_gap / delta_f_star / delta_r_star / d_i / t_m / p_m / J`
2. **轨迹执行验证**
   对比 MV 和协作车在滚动中的纵向状态演化
3. **状态机验证**
   对比 `current_plan_gap / locked_gap / merge_state / zone_state`

### 验收标准

- 不能只验证最终是否合流完成。
- 必须验证“为什么选它、怎么走到它、执行过程中有没有漂”。

## 三、当前建议的阶段出口

## 阶段 1：S07 单 MV 数值对齐

出口标准：

1. 第一帧触发规划时，复制版内核结果与 OneStep S07 一致。
2. 局部坐标到全局坐标转换后，`p_m` 等全局量正确。
3. 参与规划的车辆纵向运动已被轨迹接管。

## 阶段 2：S07 单 MV 连续滚动对齐

出口标准：

1. 不触发规划的帧不会重算 gap。
2. 计划执行过程中轨迹连续，不漂移到别的 gap。
3. 控制区和合流区的状态转换语义正确。

## 阶段 3：多 MV 与有效可控性分支

出口标准：

1. 同帧多 MV 不抢同一个 gap。
2. 同帧多 MV 不重复占用同一协作边界车。
3. 前车不可控 / 后车不可控 / 双不可控分支都能稳定跑通。

## 阶段 4：HDV 与 Replay

出口标准：

1. 不可控车默认运动模型接入后，不破坏前面三阶段结果。
2. 数值轨迹输出已经足够稳定，才进入 SUMO Replay。
