# 细节对齐记录

## 一、文档定位

本文用于记录以下讨论主题下已经完成的细节对齐结论：

```text
如何把项目代码现在的一个共用的 ramp_merge 执行框架
    + 一个 OneStep stage2 触发重规划 + bundle 执行分支
实现为 docs/新算法实现/新算法流程唯一标准.md 中定义的新算法流程。
```

本文记录已经讨论清楚并完成统一收口的实现层细节。
本文不是正式执行计划，也不是当前代码现状说明。
本文不另立第二套权威源；后续若发现与标准正文残留不同步，应同步修订三篇文档。

本文的使用边界固定如下：

1. 只记录已经讨论清楚、并已经拍板的内容。
2. 只服务于新分支设计，不服务于 legacy 分支维护。
3. 本文所有口径以“目标算法标准”和本次讨论结论为准，不再以当前单 MV 代码行为为准。
4. 三篇文档应保持同一口径；若发现残留不同步，直接同步修订对应文档。

## 二、讨论背景与当前目标

本轮讨论的原始目标是：

```text
在现有共享 ramp_merge 执行框架内，
实现 OneStep 接入后的新算法流程，
并最终能够用项目内已适配好的近似 S07 桥接场景完成验证。
```

本轮讨论同时明确了当前最近的多 MV 验证目标：

```text
在现有 S07 rolling-entry 桥接场景基础上，
在匝道上新增一辆 local = -60 的 MV，
形成一个独立的 2-MV 连续时间滚动验证场景。
```

这里的 S07 指的是：

```text
项目里已经适配好的、几乎等价于原始 OneStep S07 的桥接场景，
不是去重新搭一个新的原始固定场景复刻版本。
```

## 三、已经明确排除在设计范围之外的内容

本轮讨论已经明确：

```text
完全不要管 legacy 控制区 / 合流区规划分支。
```

因此，后续所有设计与实现判断都遵守以下边界：

1. 不为了兼容 legacy 分支而污染新分支状态设计。
2. 不把 legacy 的计划对象、旧控制区语义、旧合流区语义作为约束。
3. 只把当前共享引擎骨架当作可复用外壳。
4. 只在确实可复用时借用已有的“执行壳子”，不借用 legacy 规划逻辑。

## 四、已经拍板的总方向

### 1. 共享执行外壳保留

当前项目里的共享 `ramp_merge` 执行框架整体保留，后续仍然沿用：

```text
step0-3
→ freeze
→ relations refresh
→ safety
→ trigger
→ stage2 planning
→ motion
→ commit
→ time advance
```

也就是说，后续不是推倒重做整套 engine，而是：

```text
保留 engine 外壳，
重构其中的 OneStep stage2 分支，
把它从“单 MV + 三车 bundle”演进为“多 MV 回合式 stage2 分支”。
```

### 2. 真正要重构的是 OneStep stage2 分支

本轮讨论已经统一认识：

```text
后续需要重构的核心不是整个 ramp_merge 引擎，
而是 onestep_stage2 这条规划 / 执行支路。
```

原因是当前这条分支仍然保留了以下单 MV 假设：

1. 只支持 1 辆活动 MV。
2. 只支持 `mv + rear + front` 三车全量 bundle。
3. 只做纵向 bundle 控制，没有完整的纵向转横向闭环。
4. gap 和车辆的最终匹配仍有依赖 `x_local` 反查的旧设计。

因此，后续目标不是修修补补，而是把它提升为：

```text
每次 trigger 的多 MV 回合式 stage2 分支。
```

## 五、验证场景层的对齐结论

### 1. 单 MV 基线场景继续保留

当前已适配好的 S05、S07 单 MV 桥接场景继续保留，用作：

1. OneStep 固定场景桥接正确性的基线。
2. 单 MV 数值结果对齐的基线。
3. 后续多 MV 改造后的回归基线。

### 2. 2-MV S07 必须是独立正式场景

已经拍板：

```text
S07 的 2-MV 验证，不要污染现有单 MV S07。
必须新增一个独立场景入口。
```

这里的“独立”是指：

1. 有独立的 scenario id。
2. 有独立的 summary。
3. 有独立的图和产物目录。
4. 不通过测试里临时注入第二辆 MV 来长期承载这条验证链。

这个独立 2-MV S07 入口不是一次性的“临时验证入口”，
而是后续正式验证链路的一部分。
该场景同时被标准正文列为标准验证载体，不能被降级为临时测试入口。

第二辆 MV 的正式初始布置口径为：

```text
相对原主 MV 的局部位置：x_local = -60
在当前 bridge 配置下对应：x_global = 6540
```

它表示：

1. 原有 rolling-entry MV 是前车。
2. 新增 `x_local = -60` 的 MV 是后车。

### 3. 场景桥接层仍然统一走 ramp_merge_onestep_scenarios

本轮讨论对场景层的判断是：

```text
当前实现阶段，ramp_merge_onestep_scenarios.py
继续作为 OneStep S05 / S07 / 2-MV S07
桥接进入 ramp_merge 的统一入口。
```

它只负责场景桥接和 case spec，不承载算法语义。
算法语义必须沉到 onestep_kernel / planner / motion / runtime / runner / validation。

但它后续不应继续停留在“单 MV case spec”上，而应向多 MV 结构演进。

后续更合理的桥接模型是：

```text
case spec 不再只包含 mv_id，
而是升级为 mv_ids + 每个 mode 下每辆 MV 的初始位置表。
```

这样：

1. S05 / S07 单 MV 场景只是多 MV 结构的特例。
2. 新的 S07 2-MV rolling 场景可以自然挂入同一桥接层。
3. 后续扩到更多 MV 或更多 OneStep 场景时，不需要再新开第二套桥接体系。

### 4. S07 2-MV 验证的角色定位

本轮讨论已经确认，S07 2-MV 场景的首要价值是：

```text
验证连续时间滚动下，
前车先触发 / 先占用 / 先进入后续状态，
后车再进入控制区时如何受已占用 gap 约束。
```

因此，这个场景的主要验证重点首先是：

1. occupied gap 约束是否生效。
2. 多 MV 是否会出现 gap 冲突。
3. bundle ownership 是否冲突。
4. 前车与后车的触发顺序、重规划顺序是否符合标准。

## 六、已经拍板的核心编号与顺序规则

这一组规则是后续所有实现和文档必须共同遵守的硬标准。

### 1. MV 处理顺序

```text
MV 按匝道 x_global 从前到后处理。
```

也就是：

```text
x_global 更大的匝道 MV 先处理，
x_global 更小的匝道 MV 后处理。
```

### 2. 主线车辆编号规则

```text
主线车按 x_global 从大到小排序：
veh_1 最靠前
veh_2 次之
...
veh_n 最靠后
```

### 3. gap 编号规则

已经拍板：

```text
gap_1 最靠前，
gap 编号越大，位置越靠后。
```

对应结构化语义为：

```text
gap_1 = gap(1, veh_2, veh_1)
gap_2 = gap(2, veh_3, veh_2)
...
gap_i = gap(i, veh_{i+1}, veh_i)
```

### 4. 防交叉规则

已经拍板：

```text
当前 MV 只能选择“本轮已占用 gap 之后”的 gap，
也就是只能选择物理上更靠后的 gap。
```

在当前标准中，这条规则等价于：

```text
若 selected_gaps_round 当前已非空，
则当前 MV 的候选 gap 只保留 gap_index > max(selected_gaps_round) 的那些。
```

其中：

```text
max(selected_gaps_round)
表示“本轮已占用 gap 的最后沿 / 物理最靠后 frontier”。
```

这条规则与以下两条共同构成当前标准中的顺序关系：

1. MV 按前到后处理。
2. gap 按前到后编号。

因此：

```text
前面先处理的前车只能占用更靠前的 gap，
后面再处理到更靠后的 MV 时，
它只能继续往后选择 gap，
从而避免纵向交叉。
```

## 七、安全检测与不可控性对齐结论

### 1. 安全检测只根据 TTC

已经拍板：

```text
安全检测只根据 TTC 来判断。
```

不再叠加其他短间距规则。

### 2. TTC 计算范围

```text
只在同物理车道内的相邻前后车之间计算 TTC。
```

当前不考虑：

1. 非相邻车辆 TTC。
2. 跨物理车道 TTC。
3. 额外的非 TTC danger 规则。

### 3. TTC 公式

对于同物理车道中的相邻前后车：

```text
rear = 后车
front = 前车
```

当前采用的 TTC 计算公式固定为：

```text
bumper_gap =
    x_front - x_rear - vehicle_length_rear

closing_speed =
    v_rear - v_front

if closing_speed <= 0:
    TTC = +∞
else:
    TTC = bumper_gap / closing_speed
```

### 4. TTC 阈值

```text
TTC_threshold = 1.5 s
```

这里的 `1.5 s` 在当前项目中被视为：

```text
本项目当前采用的工程 danger 阈值。
```

### 5. danger 规则

```text
如果 TTC < 1.5 s，
则 rear 和 front 都被记入 danger 集合。
```

### 6. 基础可控性规则

已经拍板：

```text
CAV + compliant CHV 视为可控
HDV / non-compliant 视为不可控
```

当前项目实际仍几乎是全 CAV，但结构设计上要为未来留出这层语义。

## 八、回合级集合与不可控车辆集合的对齐结论

### 1. 本轮已占用 gap 集合

每次 trigger 开始后，需要初始化：

```text
selected_gaps_round = ∅
```

这个集合的作用是：

1. 记录本轮已经被占用的 gap。
2. 为当前 MV 的防交叉筛选提供顺序边界。

### 2. 本轮不可控车辆集合

每次 trigger 开始后，需要初始化：

```text
uncontrollable_vehicles_round =
    danger 车辆
    ∪ HDV / non-compliant
```

这个集合的作用是：

1. 把本轮中不能再被其他 MV 当作协同对象的车辆统一标记出来。
2. 为当前候选 gap 的前后车局部可控性判断提供回合级约束。

### 3. round start 初值与轮内顺序约束要分开理解

这一点已经拍板：

```text
round start 只初始化：
    selected_gaps_round = ∅
    uncontrollable_vehicles_round = danger ∪ base-uncontrollable

不在 round start 预填任何 locked gap。
控制区里旧 current_plan_gap 不预占用。
```

具体含义是：

1. round start 只建立本轮空集合和 danger / base-uncontrollable 初值。
2. locked / merging 相关的占用约束，不在初始化时预灌。
3. 上一轮留在控制区中的 `current_plan_gap` 不预占用，因为控制区允许在新 trigger 下重新计算。

### 4. 轮内顺序处理时，哪些占用承诺要写入集合

当处理到某辆 MV，且它已经形成“后续 MV 必须尊重”的占用 gap 时，
就立即同步写入：

```text
将该 gap 加入 selected_gaps_round
将该 gap 的前车和后车加入 uncontrollable_vehicles_round
```

正式写入时机只有三类：

1. `merge_state == merging`：
   处理到该 MV 时，立即写入其 `locked_gap`。
2. `zone_state == merge_zone`：
   处理到该 MV 时，若 `locked_gap` 为空且有 `current_plan_gap`，先锁 gap；
   一旦形成 `locked_gap`，不论本帧 longitudinal ready 与否，都立即写入该 gap 及边界车。
3. `zone_state == control_zone`：
   处理到该 MV 且最终选出 `gap_best` 后，立即写入。

### 5. 当前 MV 处理完成后的集合更新

每处理到一辆 MV，只要该 MV 当前分支已经持有一个对后续 MV 生效的占用 gap，
就立即执行：

```text
将该 gap 加入 selected_gaps_round
将该 gap 的前车和后车加入 uncontrollable_vehicles_round
```

这意味着：

1. `merge_zone ready`
   和 `merge_zone not ready`
   都会占住已经形成的 `locked_gap`。
2. `outside_control_zone` 不写入任何 round 占用约束。
3. 顺序约束是前车处理后约束后车，不是 round start 全量预灌。

共享边界车规则也在这一层统一固定：

1. 后一辆 MV 可以选择与已占用 gap 相邻的 gap。
2. 如果相邻 gap 共享边界车，则该共享边界车必须已经在 `uncontrollable_vehicles_round` 中。
3. 因而后一辆 MV 对该候选 gap 的评分，不得再把共享边界车按“仍可自由协同”的边界车处理。

### 6. 回合级不可控集合与局部可控性不是一回事

已经统一：

```text
本轮不可控集合是回合级语义。
某个候选 gap 的前后车是否可控，则是局部语义。
```

局部可控性的推荐定义为：

```text
front_effective_controllable =
    BaseControllable(front)
    and front ∉ uncontrollable_vehicles_round

rear_effective_controllable =
    BaseControllable(rear)
    and rear ∉ uncontrollable_vehicles_round
```

## 九、控制区、合流区与执行中状态的对齐结论

### 1. 正在执行横向合流

已经拍板：

```text
正在执行横向合流的 MV，
不再重新筛 gap，
不再重规划，
不再替换 bundle。
```

它当前阶段唯一的任务是：

1. 继续执行当前横向轨迹。
2. 继续占用其 locked gap。
3. 在满足横向完成条件后进入 `merge_completed`。

这里的资源占用写入发生在轮内处理到这辆前车时，
因此后续 rear MV 看到的 frontier 会已经收紧；
但这不是 round start 阶段的统一预填。

### 2. 合流区原则

已经拍板：

```text
进入合流区即锁 gap。
合流区原则上不再重选 gap。
```

合流区的判断顺序固定为：

1. 若还未锁 gap 且存在 `current_plan_gap`，立即锁定为 `locked_gap`。
2. 若 `locked_gap` 或 bundle 缺失，则默认纵向前进，不重选 gap。
3. 若 `locked_gap + bundle` 都存在，则先用“本帧开始时真实状态”判纵向 ready。

### 3. 纵向满足后的处理

已经拍板：

```text
纵向满足条件时，立即触发横向合流。
```

并且：

1. 触发横向时，原 `active_bundle` 立即 release，`MV.active_bundle` 清空。
2. 只保留 MV 自己的 `active_lateral_trajectory`。
3. 前后协同车辆立即退出该 MV 的 `controlled_vehicle_ids`。
4. 前后协同车辆回到默认主线运动，或回到其所属的其他有效 bundle。
5. `current_plan_gap / locked_gap` 保留到 `merge_completed` 后的下一轮 `step0` 清理。

### 4. 纵向未满足时的处理

已经拍板：

```text
如果合流区内当前还不满足纵向合流判定条件，
则什么都不清。
bundle 保留，current_plan_gap 继续保留，locked_gap 继续保留。
下一帧继续执行。
```

### 5. 控制区原则

已经拍板：

```text
控制区内每次 trigger 都重算。
```

这意味着：

1. 当前真实状态要重新构造局部场景。
2. 可达 gap 重新筛选。
3. 防交叉重新筛选。
4. gap 重新打分。
5. 新的 plan object 和新的 bundle 重新生成。

同时必须补一条冻结快照约束：

```text
同一 trigger round 内，所有 MV 共用同一份冻结的主线 gap snapshot。
前车对后车的影响，只允许通过 selected_gaps_round、
uncontrollable_vehicles_round 和 frontier 传播，
不做轮内几何二次刷新。
```

同一 trigger round 内，前车对后车的影响只通过 round context 传播。
跨帧 runtime 状态采用 batch writeback：

```text
每个 MV 的 current_plan / locked_plan / bundle / lateral_trajectory 更新
先进入 round_update，
所有 MV 处理完成后统一提交。
```

### 6. 同 gap 重算的处理

这一点已经明确：

```text
即使重算后仍然选中同一个 gap，
也要生成新的 plan object 和新的 bundle。
```

也就是说：

```text
每次 trigger 都是一个新的 planning epoch。
差别只在于新旧 epoch 的 gap_id 是否相同，
而不是复用同一个旧 plan。
```

### 7. 控制区外

已经拍板：

```text
控制区外的 MV 不参与本轮 gap 筛选与打分，
按默认模型行驶。
```

## 十、纵向判定、横向完成与主线化的对齐结论

### 1. 纵向 ready 的判定时机

已经拍板：

```text
纵向 ready 用“本帧开始时的当前真实状态”来判。
```

这里强调的是：

1. 不是拿上一轮预测状态判。
2. 不是拿同一帧内新候选状态先行代替当前真实状态判。
3. 是在本帧 planning / motion 之前，先看真实世界状态。

### 2. 纵向 ready 的判定规则

当前讨论中采用的标准是：

```text
MV 与 locked_gap 前车的间距 >= G_req / 2
MV 与 locked_gap 后车的间距 >= G_req / 2
并且 MV 已到达该 plan 预测的 merge_point_x_global
```

### 3. 横向完成条件

已经拍板：

```text
abs(y - lane_2_centerline) <= 0.1 m
```

### 4. merge_completed 的语义

已经拍板：

```text
merge_completed 不是最终主线状态，
而是“横向完成后，等待下一轮 step0 变性”的中间状态。
```

### 5. 下一轮 step0 的主线化

已经拍板：

```text
当 MV 进入 merge_completed 后，
下一轮 step0 把该车变性为主线车。
之后它的行为与普通主线车一致。
```

也就是说，主线化需要同时完成：

1. `physical_lane` 变为 `lane_2`
2. `road_role` 变为 `mainline`
3. 清空与匝道 MV 规划相关的 plan / locked / bundle 引用
4. 从后续的 on-ramp MV 规划循环中退出

### 6. 默认 20 m/s 的适用范围

在本轮讨论中已经明确：

```text
默认 20 m/s 匀速前进，
是当前项目对“未进入本帧有效 stage2 控制”的默认巡航口径。
```

它适用于例如：

1. 控制区外的 MV。
2. 控制区内本轮没有可用 gap、因此不生成新 plan / bundle 的 MV。
3. 合流区内缺失 locked plan 或 bundle、因此无法继续按有效合流计划执行的 MV。

默认 20 m/s 只适用于未进入任何有效 `bundle.controlled_vehicle_ids` 的车辆。
若主线 front / rear 当前仍属于某个有效 bundle，则它们继续按 bundle 执行，
而不是被“主线车默认 20 m/s”覆盖。

它不表示：

```text
纵向 ready 之后还继续长期停留在“纯纵向 handoff”状态。
```

因为当前已经拍板的目标语义是：

```text
合流区内一旦满足纵向 ready，
就立即触发横向合流。
```

## 十一、gap 四类评分分支与 delta_f_bar / delta_r_bar 的对齐结论

### 1. 四类分支总览

已经拍板，当前控制区内每个候选 gap 的评分要分成四类：

1. 前后车都可控
2. 前车可控、后车不可控
3. 后车可控、前车不可控
4. 前后车都不可控

### 2. 前后车都可控

```text
正常 OneStep 求解与评分。
```

### 3. 前车可控、后车不可控

已经拍板：

```text
delta_r_bar = 0
```

含义是：

```text
后车一侧不允许再为当前 MV 调整纵向间隙。
```

### 4. 后车可控、前车不可控

已经拍板：

```text
delta_f_bar = 0
```

含义是：

```text
前车一侧不允许再为当前 MV 调整纵向间隙。
```

### 5. 前后车都不可控

已经拍板：

```text
delta_f_bar = delta_r_bar = 0
```

此时还要再分两种情况：

1. 如果当前 gap 长度 `<= 95 m`
2. 如果当前 gap 长度 `> 95 m`

### 6. 双不可控且 gap <= 95 m

已经拍板：

```text
保留在候选表中，
但直接给极大分 10000，
保证无论如何都不会被选中。
```

### 7. 双不可控且 gap > 95 m

已经拍板：

```text
允许它作为保底 gap 参与评分，
但仍强制 delta_f_bar = delta_r_bar = 0。
```

也就是把它当成：

```text
ego-only 进入一个已经足够大的不可控 gap 的保底分支。
```

### 8. 为什么是 95 m 而不是 85 m

已经拍板：

```text
95 m 不是论文原始 G_req，而是工程缓冲阈值。
```

它的目的不是改变纵向合流理论门槛，而是：

```text
为双不可控场景预留缓冲，
避免运行过程中 gap 再次缩小后跌破最小需要间隙。
```

### 9. 关于 OneStep 内核如何承接这四类分支

本轮讨论已经形成的判断是：

```text
不要把 OneStep 数学求解复制成四套实现。
应该让内核支持在每个候选 gap 上覆盖 delta_f_bar / delta_r_bar，
再继续使用同一套合作、投影、deadzone 和评分逻辑。
```

因此后续更自然的实现方向是：

1. 在进入 OneStep cooperation/scoring 前，先根据当前 gap 的局部可控类型改写容量。
2. 然后继续走同一套 OneStep 数学路径。

## 十二、OneStep 内核映射与 gap / 车辆 id 的对齐结论

### 1. 已明确否定的旧设计

已经拍板：

```text
gap 和车辆都应该用 id 做最终匹配。
不允许把 x_local 反查 vehicle_id 作为目标标准设计。
```

这意味着后续必须放弃：

```text
先用当前真实状态构造 local frame，
再在 best_gap 解出后按 x_local 精确匹配回真实车 id
```

这种方式不能作为最终标准。

### 2. 新的对齐方向

后续应改成：

1. 真实场景中的主线车辆和 gap 都保留稳定 id。
2. 局部场景中的主线车辆和 gap 也保留可直接映射的稳定 id。
3. OneStep 最优解返回后，直接通过 gap id / vehicle id 对回真实场景。

### 3. 文档为准改内核

本轮讨论已经拍板：

```text
当前 gap 编号方向与现有 OneStep 内核历史编号存在冲突时，
以后续标准文档为准，不保留旧编号方向。
```

这里的“改内核”只指 `cormc/ramp_merge_algorithm/onestep_kernel`。
原始 `cormc/one_step_algorithm` 不改，继续作为历史单次规划黄金基线。

也就是说，后续 `ramp_merge_algorithm/onestep_kernel` 中的 gap 编号也要统一成：

```text
gap_1 最靠前
gap 编号越大越靠后
```

这样后续 runtime、kernel、summary、图表、测试里的 gap 语言才能统一。

## 十三、runtime 状态层的对齐结论

### 1. 当前状态表达为什么不够

本轮讨论已经统一认识：

```text
只用 current_plan_gap / locked_gap / active_bundle_id / OneStepPlanBundle
这套散开的状态表达，不适合后续多 MV。
```

它的问题在于：

1. plan 信息分散在多个对象中。
2. merge point、bundle linkage、评分摘要不能稳定归位。
3. 同 gap 重算时难以表达“新的 planning epoch”。
4. 单侧可控 / 双侧不可控 bundle 形态不好表达。

### 2. 后续应围绕 richer plan object 重构

已经拍板：

```text
current_plan_gap / locked_gap 后续应升级为 richer plan object 的引用语义，
不再只保留轻量 GapRef。
```

### 3. 推荐的四层状态模型

本轮讨论形成的稳定判断是，后续 runtime 至少拆成四层：

1. `MVPlanState`
2. `GapPlan`
3. `Stage2Bundle`
4. `LateralTrajectory`

### 4. MVPlanState 后续应承载的主要内容

正式语义至少包括：

```text
mv_id
zone_state
merge_state
current_plan_gap
locked_gap
active_bundle
active_lateral_trajectory
last_plan_step
last_plan_t
```

实现层可以存为：

```text
current_plan_id
locked_plan_id
active_bundle_id
active_lateral_trajectory_id
```

但这些 id 只是 registry key，必须解析到：

```text
GapPlan
Stage2Bundle
LateralTrajectory
```

### 5. GapPlan 后续应承载的主要内容

推荐承载：


### 6. Stage2Bundle 后续应承载的主要内容

推荐承载：

```text
start_t
```


### 8. bundle 必须支持四种形态

已经形成稳定结论：

```text
Stage2 bundle 不能再假设永远是 mv + rear + front 三车全量控制。
```

后续必须支持：

1. `mv + front + rear`
2. `mv + front`
3. `mv + rear`
4. `mv only`

这对应前面已经拍板的四类 gap 可控性分支。

## 十五、拍板的时序细节

这一部分专门记录本轮已经拍板的关键时序问题。

### 1. 纵向 ready 的判断时点

```text
用本帧开始时的真实状态判断。
```

### 2. 新 plan / 新 bundle 的生成时点

```text
在本帧 trigger 中生成。
```

### 3. 新 bundle 的生效时点

已经拍板：

```text
本帧立即生效。
```

它的具体含义是：

```text
新 plan / 新 bundle 在本帧 trigger 中生成，先进入 round_update。
本轮所有 MV 处理完成后，round_update 在本帧 motion 前统一提交。
因此新 bundle 仍然是本帧立即生效，
但不是处理单个 MV 后立刻写回全局 runtime。
```

### 4. 同 gap 重算时的语义

```text
同 gap 也视为新的 planning epoch。
```

### 5. 合流区中的保留语义

```text
如果纵向未满足，
则什么都不清，
原有 current_plan / locked_plan / bundle 全部继续保留并执行。
```

### 6. 横向开始后的协同释放

```text
横向一启动，
原 active_bundle 立即 release，MV.active_bundle 清空；
前后协同车退出该 MV 的 controlled_vehicle_ids，
回到默认主线运动或其所属的其他有效 bundle；
只保留 MV 自己的 active_lateral_trajectory。
```

## 十六、当前已经形成的最终实现轮廓

基于以上全部对齐结论，当前已经形成的最终实现轮廓如下。

### 1. 外壳保留

保留共享 `ramp_merge` 主循环外壳：

```text
step0-3
→ safety
→ trigger
→ stage2 round planning
→ motion
→ commit
→ time advance
```

### 2. 新的 stage2 planner 形态

新的 `onestep_stage2` 不再是单车 planner，而是：

```text
每次 trigger 进入一个回合式 planner。
```

这个 planner 的执行骨架应是：

1. 初始化本轮集合
2. 识别主线车辆与 gap 快照
3. 按前到后顺序处理 MV
4. 对每辆 MV 按四类状态分支执行
5. 产出本帧新的纵向 bundle / 横向轨迹 / 默认运动输入

### 3. 四类 MV 分支

新的 stage2 planner 中，每辆 MV 应进入以下四类分支之一：

1. 正在执行横向合流
2. 位于合流区
3. 位于控制区
4. 尚未进入控制区

### 4. 控制区分支

控制区分支的骨架应为：

1. 可达性筛选
2. 防交叉筛选
3. 四类 gap 可控性评分
4. 选择 `J` 最小的 gap
5. 生成新的 plan object
6. 生成新的 bundle
7. 更新回合级已占用 gap 与不可控集合

### 5. 合流区分支

合流区分支的骨架应为：

1. 进入合流区即锁 gap
2. 若缺失 locked plan / bundle，则默认前进
3. 若存在 locked plan / bundle，则先看本帧真实状态是否纵向 ready
4. ready 则立即触发横向
5. 未 ready 则原 bundle 原样保留

### 6. 执行层

motion 层后续应同时支持：

1. 默认车辆运动
2. 各类 bundle 纵向执行
3. 单 MV 横向执行
4. 横向完成后的主线化切换

### 7. 状态层

runtime 层后续应围绕：

```text
MVPlanState
GapPlan
Stage2Bundle
LateralTrajectory
```

来重新组织，而不是继续围绕轻量 `GapRef` 打补丁。

### 8. OneStep 内核层

OneStep 内核后续要完成两件关键统一：

1. gap 编号方向改到与“唯一标准”一致。
2. gap / vehicle 的真实映射改成 id-first，不再用 `x_local` 反查。
3. runtime 上层不再围绕轻量 `GapRef` 打补丁，而围绕正式 plan object 语义组织。

### 9. 验证与产物层

验证层后续采用：

1. 单 MV S05 / S07 基线场景
2. 独立 2-MV S07 rolling 验证场景

产物层固定采用：

```text
scenario_summary
round_summaries
mv_summaries
cross_mv_summary
artifact_paths
```

的多 MV 结构，而不是继续停留在单 MV first-trigger 视角。

## 十七、后续正式执行时不得偏离的口径

为了避免后续正式执行时再次摇摆，下面几条口径在本文中再次统一固定：

1. MV 按匝道 `x_global` 从前到后处理。
2. `gap_1` 最靠前，gap 编号越大位置越靠后。
3. 当前 MV 只能选本轮已占用 gap 之后、也就是物理上更靠后的 gap。
4. 安全检测只基于 TTC。
5. TTC 只在同物理车道相邻前后车之间计算。
6. `TTC_threshold = 1.5 s` 是当前项目采用的工程阈值。
7. 控制区每次 trigger 都重算。
8. 同 gap 重算也要生成新的 plan object 和新的 bundle。
9. 合流区原则上不重选 gap。
10. 纵向 ready 用本帧开始时真实状态判断。
11. 本帧 trigger 生成的新 plan / bundle / 横向轨迹先进入 `round_update`，本轮所有 MV 处理完成后统一提交，并在本帧立即生效到下一状态。
12. 横向一启动，原 `active_bundle` 立即 release，`MV.active_bundle` 清空；前后协同车退出该 MV 的 `controlled_vehicle_ids`。
13. 横向完成条件是 `abs(y - lane_2_centerline) <= 0.1 m`。
14. `merge_completed` 是等待下一轮 `step0` 主线化的中间状态，不是最终主线状态。
15. legacy 控制区 / 合流区规划分支不再参与设计约束。
