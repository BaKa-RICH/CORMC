本文定义后续多 MV 扩展必须遵守的**目标算法标准**，不是当前实现现状说明。

本文只参考旧文档的排版风格，不沿用旧算法逻辑作为当前标准。

本文已与两份细节对齐记录完成统一收口。

# 一、核心状态与集合

## 1. 匝道车合流状态

```text
merge_state ∈ {
    normal,             # 尚未开始执行横向合流，可在控制区内重规划
    merging,            # 正在执行横向合流
    merge_completed     # 已完成横向合流，等待在下一轮 step0 变性为主线车
}
```

说明：

```text
normal:
    MV 还没有真正执行横向合流动作。
    如果 MV 位于控制区，则触发规划时可以重新筛选、打分并选择 gap。
    如果 MV 位于合流区，则优先使用进入合流区前已经锁定的 gap。

merging:
    MV 已经开始执行横向合流动作。
    此时不再重新筛选 gap。
    该 MV 继续执行当前横向合流轨迹，直到横向完成。

merge_completed:
    MV 已满足横向完成条件。
    在下一轮 step0 中，该车将被变性为一辆跑通的主线车。
    变性完成后，该车不再作为匝道 MV 参与后续 MV 规划循环。
```

---

## 2. 车辆区域状态

```text
zone_state ∈ {
    outside_control_zone,   # 尚未进入控制区
    control_zone,           # 控制区，可重规划 gap，但不能触发横向合流
    merge_zone,             # 合流区，原则上不再重选 gap；先判纵向，再触发横向
    out_of_scene            # 驶出仿真区域
}
```

其中：

```text
控制区长度 = 300 m
合流区长度 = 300 m
```

控制区和合流区连续排列：

```text
on-ramp 入口方向
  ↓
控制区
  ↓
合流区
  ↓
主线
```

控制区内：

```text
可以识别 gap
可以做可达性筛选、防交叉筛选、打分和重规划
可以生成或替换 bundle
不能开始横向合流
```

合流区内：

```text
原则上不再重选 gap
优先使用进入合流区前已经锁定的 gap
先用当前真实状态判断是否满足纵向合流条件
满足后才开始横向合流
```

---

## 3. 当前 plan / 锁定 plan / 当前 bundle / 当前横向轨迹

```text
current_plan_gap:
    控制区内最近一次规划得到、并仍被当前 MV 持有的 GapPlan 引用
    它不是裸 gap id，而是指向包含 gap_id、front_vehicle_id、
    rear_vehicle_id、merge_point 和评分摘要的 plan object
    它天然与当前保留的 bundle 对应

locked_gap:
    MV 进入合流区后锁定的 GapPlan 引用
    一旦锁定，合流区内原则上不再重选 gap

active_bundle:
    当前 MV 的有效控制 bundle
    其中携带：
        选中 gap 的 id
        选中 gap 的前后车 id
        预测合流点
        协同轨迹信息
        纵向控制承接所需的边界状态

active_lateral_trajectory:
    MV 横向启动后执行的横向轨迹对象
    它与 locked_gap / active_bundle 语义关联，但独立承载横向执行状态
```

说明：

```text
current_plan_gap 与 active_bundle 是绑定关系。
current_plan_gap / locked_gap 在正式语义上都是 GapPlan 引用，不是裸 gap id。
如果 bundle 继续保留并执行，则 current_plan_gap 也继续保留。
合流区内若纵向条件尚未满足，则什么都不清，bundle 和 current_plan_gap 都继续保留。
```

实现层允许使用：

```text
current_plan_id
locked_plan_id
active_bundle_id
active_lateral_trajectory_id
```

但这些 id 只是 registry key，必须能解析到正式对象：

```text
GapPlan
Stage2Bundle
LateralTrajectory
```

其中 `current_plan_gap / locked_gap` 永远不是裸 gap id。

## 4. 本轮规划集合

每次触发规划时，都要初始化两个本轮集合：

```text
selected_gaps_round:
    本轮已占用 gap 集合

uncontrollable_vehicles_round:
    本轮不可控车辆集合
```

初始化规则：

```text
selected_gaps_round = ∅

uncontrollable_vehicles_round =
    所有 danger 车辆
    ∪ 所有 HDV / non-compliant 车辆
```

说明：

```text
当前项目暂时是全 CAV 场景，
因此现阶段 uncontrollable_vehicles_round 的初值主要来自 danger 车辆。

未来扩展到 compliant CHV / HDV / non-compliant 时：
    CAV + compliant CHV 视为可控
    HDV / non-compliant 视为不可控
```

每当处理到一辆 MV，且该 MV 在本轮形成或持有一个后续 MV 必须尊重的占用 gap 时，
都要立即执行：

```text
将该占用 gap 加入 selected_gaps_round
将该 gap 的前车和后车加入 uncontrollable_vehicles_round
```

注意：

```text
占用 gap 的来源只包括三类：
    control_zone 中新选出的 gap_best
    merge_zone 中已经锁定的 locked_gap
    merging 状态下继续执行的 locked_gap

step7 初始化时不预填任何 locked_gap；
这些顺序性占用约束只在轮内处理到对应 MV 时写入。

如果前后车已经因为 danger 或车辆类型原因在集合里，则不重复加入。
本轮不可控集合是“回合级”的；
某个 gap 的前后车可控性则是“相对于当前 gap 的局部属性”，两者要同时考虑。
```

---

## 5. 主线车辆编号与 gap 编号

主线车辆编号规则：

```text
所有主线目标车道车辆按 x_global 从大到小排序

x_global 更大的车是前车
x_global 更小的车是后车

记为：
    veh_1, veh_2, ..., veh_n

其中：
    veh_1 最靠前
    veh_n 最靠后
```

gap 编号规则：

```text
gap_i = gap(i, rear_vehicle_id, front_vehicle_id)
```

具体对应为：

```text
gap_1 = gap(1, veh_2, veh_1)
gap_2 = gap(2, veh_3, veh_2)
...
gap_i = gap(i, veh_{i+1}, veh_i)
```

因此：

```text
gap 编号越小，位置越靠前
gap 编号越大，位置越靠后
MV 处理顺序按匝道 x_global 从大到小，也就是前车先处理，后车后处理。
当前 MV 只能选“本轮已占用 gap 的最后沿 gap 之后”的 gap，也就是物理上更靠后、编号更大的 gap。
```

这条编号约定在以下位置必须保持一致：

```text
主线车辆排序
gap 结构化 id
本轮已占用 gap 集合
防交叉筛选
局部场景与真实场景映射
报告与验证导出
```

# 二、安全检测与有效可控性

## 1. 安全检测只基于 TTC

每个 0.1 s 周期都进行一次 TTC 检测。

检测范围：

```text
只在同物理车道内的相邻前后车之间计算 TTC
```

即：

```text
对每一条 physical_lane：
    按 x_global 从大到小或从小到大形成相邻前后车关系
    只对相邻前后车做 TTC 判断
```

---

## 2. TTC 公式

对于同物理车道中的相邻后车 `rear` 和前车 `front`：

```text
bumper_gap =
    x_front - x_rear - vehicle_length_rear

closing_speed =
    v_rear - v_front

if closing_speed <= 0:
    TTC = +∞
else:
    TTC = bumper_gap / closing_speed
```

danger 判定阈值：

```text
TTC_threshold = 1.5 s
```

即：

```text
if TTC < 1.5 s:
    rear 和 front 都被标记为 danger
```

说明：

```text
这里只保留 TTC 规则，不再叠加其他短间距规则。
若 closing_speed <= 0，则说明后车没有继续逼近前车，不触发 danger。
```

---

## 3. 有效可控性判断

车辆原始可控性：

```text
BaseControllable(vehicle) =
    True,   if vehicle ∈ {CAV, compliant CHV}
    False,  if vehicle ∈ {HDV, non-compliant}
```

规划时真正使用的是：

```text
EffectiveControllable(vehicle) =
    BaseControllable(vehicle)
    and vehicle ∉ uncontrollable_vehicles_round
```

也就是说：

```text
本来可控的车，只要它在本轮不可控集合里，
本轮也必须按不可控车处理。
```

# 三、完整伪代码

## 1. 初始化

```text
生成初始主线车辆
生成初始匝道车辆

初始化所有车辆状态：
    x, y, v, a
    physical_lane
    road_role
    is_active

初始化所有主线车辆：
    merge_state = none

初始化所有匝道 MV：
    merge_state = normal
    zone_state = 根据初始位置判断
    current_plan_gap = None
    locked_gap = None
    active_bundle = None
    active_lateral_trajectory = None

初始化时间：
    t = 0
    step = 0
    dt = 0.1

初始化周期触发参数：
    T_plan = 2.0
    next_plan_time = 0.0

初始化 TTC 阈值：
    TTC_threshold = 1.5
```

---

## 2. 每一帧主循环

```text
while t <= T_end:

    ==================================================
    step0. 清理、变性与准备
    ==================================================

    1. 删除驶出仿真区域的车辆

    2. 对所有 merge_state == merge_completed 的匝道车：
       将其变性为主线车
       更新 physical_lane = lane_2
       更新 road_role = mainline
       清空 current_plan_gap
       清空 locked_gap
       清空 active_lateral_trajectory
       active_bundle 已在横向启动时 release，此处不再承担 bundle 清理语义
       该车后续不再作为 MV 参与匝道规划循环

    3. 清空上一帧命令缓存与下一状态缓存


    ==================================================
    step1. 边界车辆生成钩子
    ==================================================

    1. 如果边界生成模块关闭：
       本步不生成新车

    2. 如果边界生成模块开启：
       按入口队列和安全进入条件生成车辆
       新进入车辆加入当前工作区

    3. 如果新生成的是匝道 MV：
       正常参与本轮 zone_state 判断与后续触发逻辑


    ==================================================
    step2. 冻结当前状态
    ==================================================

    将当前工作区冻结为本帧只读状态 S(t)


    ==================================================
    step3. 刷新关系与几何信息
    ==================================================

    1. 刷新每条车道的车辆排序
    2. 刷新 leader / follower 关系
    3. 刷新 lane-change / merge 相关邻域关系
    4. 刷新 geometry 基线与一致性检查


    ==================================================
    step4. 刷新 MV 运行时状态
    ==================================================

    对所有仍为匝道 MV 的车辆：
        根据当前位置刷新 zone_state

    清理失效 bundle
    清理失效 controlled-vehicle 关系
    清理失效 current_plan_gap / active_bundle 引用


    ==================================================
    step5. 全局 TTC 安全检测
    ==================================================

    对每一条 physical_lane：
        只对相邻前后车计算 TTC

    将 TTC < 1.5 s 的车辆加入 danger 集合


    ==================================================
    step6. 判断是否触发规划
    ==================================================

    if t >= next_plan_time:
        trigger_plan = True
        trigger_reason = periodic

    else if 本帧存在 TTC danger:
        trigger_plan = True
        trigger_reason = safety_alert

    else if 本帧有 MV 新进入控制区:
        trigger_plan = True
        trigger_reason = MV_enter_control_zone

    else:
        trigger_plan = False
        trigger_reason = none
```

---

## 3. 不触发规划时

```text
if trigger_plan == False:

    对所有仍在 merging 的 MV：
        继续执行 active_lateral_trajectory

    对所有有效 active_bundle：
        对 bundle.controlled_vehicle_ids 内的车辆执行 bundle 纵向控制

    对所有不在任何有效 bundle.controlled_vehicle_ids 中、
    且不在 active_lateral_trajectory 中的车辆：
        默认 20 m/s 行驶

    推进车辆状态
    更新时间
    continue
```

---

## 4. 触发规划时

```text
if trigger_plan == True:

    ==================================================
    step7. 初始化本轮规划集合
    ==================================================

    selected_gaps_round = ∅

    uncontrollable_vehicles_round =
        {所有 danger 车辆}
        ∪ {所有 HDV / non-compliant 车辆}

    round_update = ∅

    注意：
        此时不预填任何 locked_gap
        占用约束只在轮内顺序处理到对应 MV 时写入
        selected_gaps_round / uncontrollable_vehicles_round / tail_frontier_gap_index
        是本轮 planner 内即时推进的 round context

        current_plan_gap / locked_gap / active_bundle / active_lateral_trajectory
        等跨帧 runtime 状态，不在处理单个 MV 后立即写回全局 runtime；
        每个 MV 的持久状态变更先写入 round_update


    ==================================================
    step8. 识别主线 gap 快照
    ==================================================

    1. 取目标主线车道上的所有车辆
    2. 按 x_global 从大到小排序：
       veh_1, veh_2, ..., veh_n
    3. 构造 gap：
       gap_1 = gap(1, veh_2, veh_1)
       gap_2 = gap(2, veh_3, veh_2)
       ...
    4. 保存本帧 gap 快照
       同一 trigger round 内所有 MV 共享该快照
       轮内不因前车规划结果重新刷新几何


    ==================================================
    step9. 按匝道 x_global 从大到小处理所有 MV
    ==================================================

    也就是：
        前车先处理
        后车后处理

    for each MV in on-ramp order:
        按以下四种情况分支处理
```

# 四、四类 MV 分支

## 情况 1：MV 正在执行合流

```text
if MV.merge_state == merging:

    1. 将 MV.locked_gap 加入 selected_gaps_round

    2. 将 MV.locked_gap 的前车和后车加入 uncontrollable_vehicles_round

    3. 继续执行当前横向合流轨迹

    4. 判断是否完成横向合流：
       if abs(y_mv - lane_2_centerline) <= 0.1:
           MV.merge_state = merge_completed

    5. continue
```

说明：

```text
正在执行合流的 MV 不再重新筛 gap、不再重规划、不再替换 bundle。
这里的占用写入发生在本轮处理到该 MV 的时刻，不是 round start 初始化时统一预填。
它唯一的任务是继续执行横向轨迹，并在满足横向完成条件后进入 merge_completed。
```

---

## 情况 2：MV 位于合流区

```text
if MV.zone_state == merge_zone and MV.merge_state != merging:

    1. 若 MV.locked_gap 为空且 MV.current_plan_gap 不为空：
       立即将 MV.current_plan_gap 锁定为 MV.locked_gap

    2. if MV.locked_gap 不为空：
           立即将 MV.locked_gap 加入 selected_gaps_round
           立即将该 gap 前后车加入 uncontrollable_vehicles_round

    3. if MV.locked_gap 为空:
            MV 默认 20 m/s 行驶
            continue

    4. if MV.active_bundle 为空:
           MV 默认 20 m/s 行驶
           continue

    5. 使用本帧开始时的当前真实状态，
       判断是否满足纵向合流条件

       纵向合流条件：
            MV 与 locked_gap 前车的间距 >= G_req / 2
            MV 与 locked_gap 后车的间距 >= G_req / 2
            MV 已到达或越过当前预测合流点

    6. if 满足纵向合流条件:
            触发横向合流
            为 MV 生成 active_lateral_trajectory
            MV.merge_state = merging

            横向一启动：
                release 原 active_bundle
                MV.active_bundle = None
                前后协作车立即退出该 MV 的 controlled_vehicle_ids
                前后协作车回到默认主线运动，或回到其所属的其他有效 bundle
                MV 后续只执行 active_lateral_trajectory
                current_plan_gap / locked_gap 保留到 merge_completed 后的 step0 清理

            continue

    7. else:
            什么都不清
            MV.locked_gap 保留
            MV.current_plan_gap 保留
            MV.active_bundle 保留
            下一帧继续执行已有 bundle

            continue
```

说明：

```text
合流区内的原则是：
    进入合流区即锁 gap
    不再重选 gap
    先判纵向，再触发横向
    只要 locked_gap 已形成，就在轮内处理到该 MV 时立即占用并写入集合
```

---

## 情况 3：MV 位于控制区

```text
if MV.zone_state == control_zone:

    --------------------------------------------------
    3.1 可达性筛选
    --------------------------------------------------

    从本帧 gap 快照中筛出所有可达 gap

    if 可达 gap 集合为空:
        MV.current_plan_gap = None
        不生成新 bundle
        MV 默认 20 m/s 行驶
        continue


    --------------------------------------------------
    3.2 防交叉筛选
    --------------------------------------------------

    根据 selected_gaps_round，确定当前本轮已占用 gap 的最后沿 /
    物理最靠后已占用 gap 的 frontier
    也就是 selected_gaps_round 中 gap_index 最大者

    当前 MV 只能选择：
        “本轮已占用 gap 集合中最后沿 gap”之后的 gap
        也就是 index 更大、物理上更靠后的 gap

    if 防交叉筛选后的候选 gap 集合为空:
        MV.current_plan_gap = None
        不生成新 bundle
        MV 默认 20 m/s 行驶
        continue


    --------------------------------------------------
    3.3 对候选 gap 逐个打分
    --------------------------------------------------

    对每一个候选 gap_j：

        1. 基于本轮冻结 gap snapshot 与当前 MV 当前真实 ego 状态，
           构造该候选 gap 的 OneStep 局部评估输入

           要求：
               真实场景中的主线车辆和 gap 都必须保留 id
               局部场景中的主线车辆和 gap 也必须保留同一套 id
               不允许靠 x_local 反查 vehicle_id
               不允许用临时 gap:step:index 作为最终匹配依据

        2. 判断当前 gap_j 的前后车可控性

           front_effective_controllable =
               BaseControllable(front)
               and front ∉ uncontrollable_vehicles_round

            rear_effective_controllable =
                BaseControllable(rear)
                and rear ∉ uncontrollable_vehicles_round

           说明：
               允许候选 gap 与已占用 gap 相邻并共享一个边界车
               但该共享边界车必须已经在 uncontrollable_vehicles_round 中
               因此该候选 gap 的评分会自然落入单侧不可控或双侧不可控分支

        3. 进入 gap 四类评分分支
```

---

## 情况 3 的评分四分支

每个候选 gap 的评分结果必须形成 `gap_row`。
`gap_rows` 是每个 MV 在每次 trigger round 中的正式中间产物，不是临时 debug 输出。

每个 `gap_row` 至少包含：

```text
gap_id
gap_index
front_vehicle_id
rear_vehicle_id
reachable
filtered_by_frontier
controllability_branch
delta_f_bar
delta_r_bar
delta_f_star
delta_r_star
d_i
t_m
p_m
J
is_selected
```

`gap_rows` 归入 `mv_summaries`，并可通过 `artifact_paths` 导出。

### 分支 A：gap 前后车均可控

```text
if front controllable and rear controllable:

    正常 OneStep 求解

    正常计算：
        delta_f_bar
        delta_r_bar
        delta_f_star
        delta_r_star
        d_i
        t_m
        p_m
        J
```

---

### 分支 B：gap 前车可控、后车不可控

```text
if front controllable and rear uncontrollable:

    将后车可调整容量设为 0：
        delta_r_bar = 0

    前车仍可正常参与协同：
        delta_f_bar 正常计算

    if 单侧容量仍不足以弥补缺口:
        保留该 gap 在候选表中
        直接赋极大分：
            J = 10000
    else:
        正常继续 OneStep 求解与打分
```

说明：

```text
此时所有可调整量只能由前车承担。
```

### 分支 C：gap 后车可控、前车不可控

```text
if rear controllable and front uncontrollable:

    将前车可调整容量设为 0：
        delta_f_bar = 0

    后车仍可正常参与协同：
        delta_r_bar 正常计算

    if 单侧容量仍不足以弥补缺口:
        保留该 gap 在候选表中
        直接赋极大分：
            J = 10000
    else:
        正常继续 OneStep 求解与打分
```

说明：

```text
此时所有可调整量只能由后车承担。
```

---

### 分支 D：gap 前后车均不可控

```text
if front uncontrollable and rear uncontrollable:

    令：
        delta_f_bar = 0
        delta_r_bar = 0

    if 当前 gap 长度 > 95 m:
        允许作为保底 gap 参与评分
        强制：
            delta_f_star = 0
            delta_r_star = 0
        直接沿用 OneStep 目标函数，
        但协同代价退化为 0，
        只保留 ego displacement / timing 代价

    else:
        保留该 gap 在候选表中
        直接赋极大分：
            J = 10000
```

说明：

```text
95 m 而不是 85 m，
是为了给不可控双侧场景预留缓冲，避免运行过程中间隙再次缩小后跌破 G_req。
```

---

## 情况 3 的选优与 bundle 生成

```text
对当前 MV 的所有候选 gap 评分完成后：

    1. 选择 J 最小的 gap_best

    2. 基于 gap_best 生成新的 GapPlan
       并将该 plan 记录为 MV.current_plan_gap

    3. 按该 GapPlan 对应 gap 的局部可控状态生成 bundle
```

bundle 生成四分支：

### 分支 A：前后都可控

```text
记录当下真实三车边界状态：
    MV
    selected rear
    selected front

生成完整 bundle
用新 bundle 替换旧 bundle
```

### 分支 B：仅前车可控

```text
只记录：
    MV
    selected front

后车不进入 bundle

生成“MV + 前车” bundle
用新 bundle 替换旧 bundle
```

### 分支 C：仅后车可控

```text
只记录：
    MV
    selected rear

前车不进入 bundle

生成“MV + 后车” bundle
用新 bundle 替换旧 bundle
```

### 分支 D：前后都不可控

```text
只记录：
    MV

前后车都不进入 bundle

生成仅 MV bundle
用新 bundle 替换旧 bundle
```

处理完当前 MV 后，必须执行：

```text
将 gap_best 加入 selected_gaps_round
将 gap_best 的前后车加入 uncontrollable_vehicles_round
将 MV.current_plan_gap / MV.active_bundle 等持久状态变更写入 round_update
```

然后：

```text
continue
```

```text
if MV.zone_state == outside_control_zone:
    MV 默认 20 m/s 行驶
    continue
```

说明：

```text
控制区外的 MV 不参与本轮 gap 筛选与打分。
```

# 五、bundle 与轨迹管理

## 1. bundle 的保留与替换

```text
控制区内：
    每次触发规划后，都允许用新 bundle 替换旧 bundle

合流区内：
    不再重选 gap
    若纵向条件未满足，则旧 bundle 保留并继续执行
```

---

## 2. bundle 控制对象

```text
双可控：
    bundle 控制 MV + 前车 + 后车

仅前可控：
    bundle 控制 MV + 前车

仅后可控：
    bundle 控制 MV + 后车

双不可控：
    bundle 只控制 MV
```

---

## 3. 默认运动

```text
凡是不在当前有效 bundle 中的车辆：
    默认按 20 m/s 行驶
```

主线车若属于某个有效 `bundle.controlled_vehicle_ids`，则按该 bundle 执行；
只有不属于任何有效 bundle 的主线车才默认 20 m/s。

这包括：

```text
控制区外 MV
控制区内本轮没有选到 gap 的 MV
横向合流启动后退出纵向协同的前后车
所有普通主线车
```

---

## 4. 横向启动时释放 bundle

```text
纵向 ready 后一旦启动横向合流，纵向协作阶段结束。

此时必须 release 原 active_bundle，并清空 MV.active_bundle。

active_lateral_trajectory 成为 MV 后续唯一执行对象。

current_plan_gap / locked_gap 继续保留，用于记录本次横向合流来源，
并在 merge_completed 后的下一轮 step0 清理。
```

```text
if abs(y_mv - lane_2_centerline) <= 0.1:
```

# 七、压缩版伪代码

```text
初始化：

    初始化主线车辆与匝道车辆
    初始化 MV 状态：
        merge_state = normal
        zone_state = 根据初始位置判断
        current_plan_gap = None
        locked_gap = None
        active_bundle = None
        active_lateral_trajectory = None

    T_plan = 2.0
    next_plan_time = 0.0
    TTC_threshold = 1.5


while t <= T_end:

    1. step0：
       删除驶出车辆
       将 merge_completed 的 MV 变性为主线车
       清空上一帧缓存

    2. step1：
       如有需要，执行边界车辆生成

    3. step2：
       冻结当前状态 S(t)

    4. step3：
       刷新车道排序、前后车关系和几何信息

    5. 刷新 MV 的 zone_state、bundle 和运行时状态

    6. 只在同物理车道相邻前后车之间计算 TTC
       TTC < 1.5 s 的车辆记为 danger

    7. 判断是否触发规划：
       periodic / safety_alert / MV_enter_control_zone

    8. 若不触发：
       正在横向合流的 MV 继续跑横向轨迹
       有效 bundle.controlled_vehicle_ids 内车辆继续跑 bundle
       其他不在 bundle / lateral trajectory 中的车辆默认 20 m/s
       推进状态并进入下一帧

    9. 若触发：
       初始化：
            selected_gaps_round = ∅
            uncontrollable_vehicles_round =
                danger 车辆 ∪ HDV / non-compliant
            round_update = ∅
            不预填任何 locked_gap

        识别 lane_2 主线 gap
        主线车按 x_global 从大到小编号
        gap 按结构化 id 编号
        同一 trigger round 内所有 MV 共用该冻结快照

        按匝道 x_global 从大到小依次处理 MV：

           情况 1：MV 正在执行合流
               占用 locked_gap
               前后车加入不可控集合
               继续横向轨迹
               若 y 到达目标车道中心线，则 merge_completed

            情况 2：MV 位于合流区
                若未锁 gap，则锁 current_plan_gap
                若已有 locked_gap，则立即占用并写入本轮集合
                若无 locked_gap，则默认行驶
                若有 locked_gap 但无 bundle，则默认行驶
                否则用当前真实状态判断纵向条件
                若满足，则触发横向合流并置 merging，release active_bundle
                若不满足，则 bundle 保留并继续执行

            情况 3：MV 位于控制区
                先做可达性筛选
                再做防交叉筛选
                候选 gap 仅保留 index > 本轮已占用 gap 最后沿 index 的那些
                再对每个候选 gap 做四类可控性分支评分
                选 J 最小的 gap_best
                按四类可控性分支生成 bundle
                将 gap_best 加入已占用 gap 集合
                将 gap_best 前后车加入不可控集合
                将持久状态变更写入 round_update

           情况 4：MV 尚未进入控制区
               默认 20 m/s 行驶

        所有 MV 处理完成后：
            将 round_update 统一提交到 runtime

    10. 推进所有车辆状态

    11. 更新时间：
        t = t + dt
        step = step + 1
```

# 八、实现时必须遵守的约束

```text
1. gap 和车辆必须用 id 映射，不允许依赖 x_local 反查 vehicle_id
2. 合流区内原则上不再重选 gap
3. 单侧不可控时，要把不可控一侧的可调整容量置 0
4. 双侧不可控时，95 m 以下必须直接判为极大分
5. 默认 20 m/s 是当前项目阶段性约定，不代表未来最终主线模型
6. 验证与报告导出的顶层结构固定为：
       scenario_summary
       round_summaries
       mv_summaries
       cross_mv_summary
       artifact_paths
7. gap_rows 是 mv_summaries / artifact_paths 下的正式中间产物
8. 事件导出采用最小正式事件集，用于 summary / validation / report，不引入复杂事件系统
9. 最小事件集包括：
       trigger_round
       gap_evaluation
       bundle_created
       bundle_released
       current_plan_updated
       locked_gap_created
       lateral_started
       lateral_completed
       mainline_converted
10. merge_completed 不是最终主线状态，只是等待下一轮 step0 变性
11. 原始 cormc/one_step_algorithm 不改，继续作为历史单次规划黄金基线
12. 新算法只改 cormc/ramp_merge_algorithm/onestep_kernel 及其上层 runtime / planner / motion / runner / validation
```

# 九、标准验证载体

标准验证链路必须包含独立 2-MV S07 rolling 场景。
该场景不是临时测试替身，而是多 MV round 语义的正式验证载体。

场景要求：

```text
在现有 S07 rolling-entry 桥接场景基础上新增第二辆匝道 MV
第二辆 MV 的局部位置为 x_local = -60
在当前 bridge 配置下对应 x_global = 6540
原有 rolling-entry MV 是前车
新增 MV 是后车
两辆 MV 均按普通 MV 处理，不引入特殊测试逻辑
```

该场景至少验证：

```text
前车先处理、后车后处理
selected_gaps_round 的 frontier 传播
uncontrollable_vehicles_round 向后车传播
相邻 gap 共存时共享边界车按不可控处理
bundle 生命周期
locked_gap -> merging -> merge_completed -> step0 主线化
```

当前实现阶段，OneStep S05 / S07 / 2-MV S07 验证统一经 `ramp_merge_onestep_scenarios.py` 进入 `ramp_merge`。
该文件只负责场景桥接和 case spec，不承载算法语义。
算法语义必须沉到 `onestep_kernel / planner / motion / runtime / runner / validation`。
