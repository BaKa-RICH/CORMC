## 1. 文档定位

本文是新算法正式迭代的执行地图，不是新的算法标准，也不是代码实现记录。

阶段 0 的目标是把三篇权威文档中的算法语义转换为后续阶段可追踪、可测试、可交接的工程 checklist，并把 2-MV S07 rolling 场景前移为阶段 1 起持续陪跑的贯穿验证载体。

本文只做计划和规格映射：

- 不修改 `planner` / `motion` / `onestep_kernel` / `runner` 行为。
- 不新增真实 scenario code。
- 不新增测试文件。
- 不替代三篇权威文档。
- 不把阶段 1-8 的任务级实现细节一次性写死。

后续每个阶段真正开工前，应基于本文再制定该阶段的任务级执行计划。

## 4. 阶段合并与拆分建议

### 4.1 可以连续推进或弱合并的阶段

- 阶段 0 与阶段 1 可以连续推进。
  - 阶段 0 输出 2-MV S07 骨架设计。
  - 阶段 1 直接把该设计落到 catalogue/load/runtime admission 和 stage2 expected-failure 测试。

- 阶段 2 中 runtime 状态模型与安全/gap/id-first 基础可以在同一实现波次推进。
  - 但测试应分层提交，避免 TTC、gap 编号、plan object 失败互相掩盖。

- 阶段 5 与阶段 6 可以连续排期。
  - bundle lifecycle 是 merge lifecycle 的前置。
  - 但不建议合成一个不可拆的大改。

- 阶段 7 的 summary 字段可以从阶段 4 开始逐步长出。
  - 阶段 7 只做正式化收口，不应等到阶段 7 才第一次生成多 MV summary。

### 4.2 不建议合并的阶段

- 阶段 3 不应和阶段 4 合并。
  - 阶段 3 是 kernel 评分语义。
  - 阶段 4 是 trigger round 编排语义。
  - 合并会导致 scoring 错误和 round 错误难以定位。

- 阶段 4 不应和阶段 5/6 合并。
  - 先让多 MV 选 gap / 占用 / frontier 可观察，再推进 bundle 和 lateral lifecycle。

- 阶段 8 不应前置成必须项。
  - plot 可以早期辅助观察。
  - SUMO replay 应在算法状态和 trajectory 语义稳定后再正式接入。

## 6. TDD 分层策略

### 6.1 单元测试

用于锁定纯语义和小函数，不依赖长时间 runner：

- TTC 计算与 danger 判定。
- gap 编号、front/rear 身份和 id-first 映射。
- base controllable 与 effective controllable。
- 四类 controllability 分支。
- 95m 双不可控保底规则。
- `J = 10000` row 保留规则。
- 四种 bundle controlled vehicle set。

### 6.2 Planner 集成测试

用于验证 trigger round 内的状态推进：

- 冻结 gap snapshot 在同一 round 内被所有 MV 共享。
- MV 处理顺序按匝道 `x_global` 从大到小。
- `selected_gaps_round` 和 `tail_frontier_gap_index` 正确推进。
- 后车候选 gap 被 frontier 正确过滤。
- `uncontrollable_vehicles_round` 对共享边界车生效。
- 所有 MV 的 runtime 更新先进入 round update，round 结束后统一提交。

### 6.3 Motion / Lifecycle 集成测试

用于验证跨帧行为：

- bundle 保留、替换、release。
- 旧 controlled states 清理。
- 不在有效 bundle 内的车辆默认运动。
- merge-zone 锁 gap。
- 纵向 ready 判断。
- 横向启动。
- `merging` 期间不重选 gap、不替换 bundle。
- `merge_completed` 与下一轮 step0 主线化。

### 6.4 Runner Rolling 测试

用于验证长时间连续滚动不退化为单 step：

- S05 单 MV plan-step0 / rolling-entry 回归。
- S07 单 MV plan-step0 / rolling-entry 回归。
- 2-MV S07 rolling-entry 贯穿陪跑。
- 每阶段只打开与本阶段相关的断言，其余后续断言可暂时 expected failing 或仅作为人工观察项。

### 6.5 Summary / Validation 测试

用于验证正式验收语言：

- `scenario_summary` 基本信息完整。
- `round_summaries` 能解释每个 trigger round。
- `mv_summaries` 能解释每个 MV 的候选、分支、选择、bundle、lifecycle。
- `cross_mv_summary` 能检查 gap conflict、frontier、uncontrollable、bundle ownership。
- 旧 `first_trigger_*` 字段可作为兼容字段暂留，但不作为新算法正式验收主视角。

### 6.6 Plot / Artifact 验收

用于辅助人工判断：

- `x-t` 图观察空间顺序、gap 选择、滚动连续性。
- `v-t` 图观察 bundle 控制、release、默认运动。
- merge lifecycle 阶段增加 `y-t` 或 lifecycle timeline 设计。
- artifact 路径归入 `artifact_paths`。

## 7. 2-MV S07 骨架测试设计

### 7.1 正式场景身份

- 场景 ID: `RM-ONESTEP-S07-2MV-ROLLING-ENTRY`
- 来源: 当前 S07 rolling-entry bridge 场景。
- 接入方式: 扩展 `ramp_merge_onestep_scenarios` catalogue/spec 层。
- 禁止方式: 不允许在测试里临时复制 scenario dict 或手动注入第二辆 MV 作为长期方案。

### 7.2 车辆布局

- 原 rolling-entry MV:
  - 角色: 前车 MV。
  - 初始 `x_global = 6600`。
  - 继续沿用当前 S07 rolling-entry 主 MV 身份。

- 新增后车 MV:
  - 建议 vehicle id: `S07_MV_REAR`。
  - 局部位置: `x_local = -60`。
  - 当前 bridge 下全局位置: `x_global = 6540`。
  - 车辆类型: 普通 on-ramp MV。
  - 特殊逻辑: 无。

### 7.3 分阶段断言打开路线

| 阶段 | 2-MV S07 验证内容 | 断言强度 |
|---|---|---|
| 1 | scenario id 可加载; 两辆 MV 均在 initial vehicles; runtime 有两个 MV; stage2 runner exposes the current single-MV limit as expected failure | required |
| 2 | TTC/gap/id-first/runtime foundation observes 2-MV initial/runtime/gap snapshot structure; stage2 multi-MV runner success is not required | required + observation |
| 3 | 后车相关候选 gap 可观察到单侧/双侧不可控分支输入趋势 | observation / progressive |
| 4 | 前车先处理、后车后处理；frontier 传播；后车不能选同 gap 或 frontier 之前 gap；无同轮 gap 冲突 | required |
| 5 | bundle ownership、replacement、旧 controlled states 清理、release 行为正确 | required |
| 6 | locked gap、merging、merge_completed、step0 主线化在长滚动中可闭环 | required |
| 7 | 五层 summary 和 validation 能正式解释 2-MV S07 | required |
| 8 | 图、artifact、SUMO replay 能消费 2-MV S07 新算法输出 | required / artifact |

### 7.4 早期 expected-fail 规则

阶段 1 接入 2-MV S07 后，允许后续算法语义断言暂时不通过，但必须满足：

- 失败原因与后续阶段待实现能力一致。
- 失败测试或 observation 项必须标注对应阶段。
- 不允许因为当前 stage2 仍是单 MV 限制而把 2-MV S07 场景从 catalogue 中移除。
