# 细节对齐记录 v1

## 1. 文档定位

本文是三篇文档统一口径后的补充对齐记录，用来固定实现层、场景层、runtime 状态层和产物层的细节。
本文不是新的算法标准正文，也不是正式执行计划。
本文不另立第二套标准；后续应与标准正文同步维护。

本文的作用有两个：

1. 在正式实现前，把已经确认的语义钉死，避免后续实现时再把 gap 编号、MV 顺序、bundle 语义、不可控集合、summary 口径拆成两套。
2. 给实现提供一份无歧义的补充对齐记录。

本文与另外两篇文档的关系统一如下：

1. `docs/新算法实现/新算法流程唯一标准.md`
   是目标算法正文。
2. 本文
   是三篇文档统一口径后的补充对齐记录。
3. `cormc/one_step_algorithm`
   保持不动，继续作为历史单次规划黄金基线。
4. 当前 `ramp_merge_algorithm` 的真实代码
   只用于说明现状，不用于反向约束新实现。

三篇文档如果仍残留历史不同步，应以本轮统一后形成的共同口径为准，
不再保留“待回写到正文”或“若未点名冲突就回正文”的临时仲裁语气。

## 2. 已固定的边界与不做事项

这轮实现边界已经固定，不再摇摆：

1. 后续实现永远以 `新算法流程唯一标准.md` 为最终目标语义，不以当前 stage2 的旧行为为真值。
2. `cormc/one_step_algorithm` 不改，继续只承担历史单次规划基线角色。
3. 真正要演化的是 `cormc/ramp_merge_algorithm/onestep_kernel` 以及其上的 runtime / planner / motion / runner。
4. `legacy` 控制区/合流区规划分支这轮完全不管。它跑不起来也没关系，有 bug 也没关系，后面会整体移除。
5. 不做“兼容旧 gap1/gap4 标签语义”的长期保留。
6. 不建议在外层再打一层长期适配补丁去修正文档与内核的冲突；应直接把新规则沉到正式内核与正式 runtime 语义里。

这意味着：

1. 旧 `test_ramp_merge_onestep_stage2_*` 里把 `best_gap_id == gap4` 当真值的断言，后续都应该按新标准重写。
2. 以后做数值对齐时，优先比较的是：
   `front_vehicle_id`、`rear_vehicle_id`、gap interval、`delta_f_star`、`delta_r_star`、`d_i`、`t_m`、`p_m`、`J`。
3. 旧 label 只能作为历史遗留现象看待，不能继续作为正式验收口径。

## 3. 当前真实代码现状判断

当前仓库里真实存在的东西，不是“新算法已经整体替换旧流程”，而是：

1. 一个共用的 `ramp_merge` 执行外壳。
2. 一个 `legacy` 控制区/合流区规划分支。
3. 一个 `OneStep stage2` 的“触发重规划 + bundle 纵向执行”分支。

当前 `OneStep stage2` 已经真实具备的能力：

1. 触发规划时，用当前真实状态为某个 MV 重建 local frame。
2. 调用复制到 `ramp_merge_algorithm/onestep_kernel` 下的 OneStep 求解逻辑。
3. 生成 bundle。
4. 在滚动仿真中用 bundle 执行纵向控制。

当前 `OneStep stage2` 还没有完成的关键能力：

1. 它明确只支持单 MV，代码里有 `_resolve_single_active_mv_id(...)` 的硬限制。
2. 它没有正式的多 MV round 规划语义。
3. 它没有完整的 `locked_gap -> merging -> merge_completed -> step0 主线化` 生命周期。
4. 它没有正式接入四类可控性分支。
5. 它没有把单侧不可控、双侧不可控、95m 保底规则沉到底层求解链路。
6. 它的 summary / analysis / tests 仍然主要是单 MV 视角。

因此，后续工作不是“给现有 stage2 外面再补几层 if”，而是：

1. 保留共用执行外壳。
2. 把当前单 MV stage2 分支演化成正式 multi-MV round planner。
3. 把正式 gap 语义、四类分支、bundle 语义、merge lifecycle 和产物口径，整体沉到正式实现里。

## 4. 已拍板的核心语义

### 4.1 gap 正式身份与编号方向

gap 的正式语义已经固定：

1. 主线车辆按 `x_global` 从大到小排序。
2. `veh_1` 最靠前，`veh_n` 最靠后。
3. `gap_1 = gap(1, veh_2, veh_1)`。
4. gap 编号越小，物理位置越靠前。
5. gap 编号越大，物理位置越靠后。

这里要特别固定两件事：

1. 正式 gap 身份以 `front_vehicle_id`、`rear_vehicle_id` 和当前 round 的 gap interval 为主，不以旧 `gap1/gap4` 名字为主。
2. 不建议保留“内核内部一套旧编号，外层再翻译成新编号”的长期双层语义。

如果实现里为了复用局部函数，短暂出现内部辅助顺序，那也只能是函数内部临时变量，不得泄漏到：

1. runtime 中的正式 `GapRef`
2. events
3. summary
4. tests
5. 对外的 gap_rows 导出

### 4.2 多 MV 的处理顺序与防交叉规则

1. MV 处理顺序按匝道 `x_global` 从大到小。
2. 也就是前车先处理，后车后处理。
3. 本文后续所有涉及多 MV round 的描述，都按这一正式口径书写。

与此绑定的防交叉规则也已经固定：

1. 当前 MV 只能选“本轮已占用 gap 的最后沿之后”的 gap。
2. 这里的“之后”指物理上更靠后。
3. 也就是 gap 编号必须更大。

正式术语统一改用：

1. `tail_frontier_gap_index`
   表示本轮已占用 gap 中物理最靠后的那个 gap 编号。

于是 round 级规则可以写成：

1. 若 `selected_gaps_round` 为空，则当前 MV 可以从所有可达候选 gap 中继续筛选。
2. 若 `selected_gaps_round` 非空，则当前 MV 只能考虑 `index > tail_frontier_gap_index` 的 gap。
3. 这条规则是多 MV 顺序约束，不是 reachability 约束，不是 controllability 约束，也不是 score 约束。

### 4.3 同一轮使用冻结快照，不做轮内几何重建

1. 同一次 trigger round 内，所有 MV 共享同一份冻结的主线 gap 快照。
2. 前一辆 MV 处理完后，不在同一轮里用它的新规划结果去重建后一辆 MV 的局部几何。
3. 也就是说，同一轮内不做“前车改了主线几何，后车立刻看更新后几何”的二次刷新。

前车对后车的影响，只允许通过 round 级上下文传播：

1. `selected_gaps_round`
2. `uncontrollable_vehicles_round`
3. `tail_frontier_gap_index`

这条约束的意义很重要：

1. 它保证同一轮中的所有评分，都是基于同一帧真实快照。
2. 它避免把“轮内资源占用语义”和“轮内几何再演化语义”混成两层，导致排查困难。

### 4.4 已占用 gap 与共享边界车的规则

共享边界车是允许的，但规则必须是单一的，不再引入第二套长期保留语义。

正式口径如下：

1. `selected_gaps_round` 用来表达“本轮哪些 gap 已经被占用”。
2. `uncontrollable_vehicles_round` 用来表达“本轮哪些边界车已经不能再按可控边界车处理”。
3. 不额外引入长期正式的 `reserved_vehicle_ids` 语义层。

如果实现细节上为了方便写代码，临时需要一个派生缓存，也只能满足下面限制：

1. 它只能是 `selected_gaps_round` 和 `uncontrollable_vehicles_round` 的内部展开结果。
2. 它不能成为第三套对外暴露的正式规则。

共享边界车的含义是：

1. 前一辆 MV 选中某个 gap 后，后一辆 MV 仍然允许选中与它相邻、并共享一个边界车的 gap。
2. 但是这个共享边界车此时必须已经在 `uncontrollable_vehicles_round` 里。
3. 因而后一辆 MV 对这个相邻 gap 的评分，不能再落入“双侧可控”分支，而会自然落入“单侧不可控”或“双侧不可控”分支。

这个设计的核心是：

1. 允许相邻 gap 共存。
2. 但不允许同一辆边界车在同一轮里被两个 MV 同时当作“仍可自由协同调整”的资源。

### 4.5 已经进入 merge_zone 或正在 merging 的 MV 要先占住资源

front MV 如果已经持有 `locked_gap`，它对 round 资源的占用必须在轮内处理到该 MV 时立即生效。

正式规则：

1. 若 MV 正在 `merging`，则处理到该 MV 时立即占用自己的 `locked_gap`。
2. 若 MV 位于 `merge_zone` 且已经有 `locked_gap`，则处理到该 MV 时也立即占用自己的 `locked_gap`。
3. 该 `locked_gap` 的 front / rear 车辆必须立即加入 `uncontrollable_vehicles_round`。

这意味着：

1. 后面的 control-zone MV 看到的 frontier，应该已经包含这些被锁定或正在执行中的 gap。
2. 后面的 MV 不得再把这些边界车当作本轮仍可自由协同的资源。
3. 这种“先占住资源”的效果来自前车先处理后的顺序推进，而不是 round start 的统一预填。

## 5. 不可控集合与四类可控性分支

### 5.1 uncontrollable_vehicles_round 的正式身份

`uncontrollable_vehicles_round` 是 round 级集合，不是车辆永久属性。

每次 trigger round 开始时：

1. `selected_gaps_round = ∅`
2. `uncontrollable_vehicles_round = danger 车辆 ∪ HDV / non-compliant`

考虑到当前项目阶段还是全 CAV 场景，现阶段初始不可控集合主要来自 `danger`。

step7 初始化阶段不预填任何 locked gap；
round 内的顺序性占用约束，只在处理到对应 MV 时增量写入。

每处理到一辆 MV，只要该 MV 当前分支已经形成或持有一个对后续 MV 生效的占用 gap，
就必须执行：

1. 将该 MV 最终占用的 gap 加入 `selected_gaps_round`
2. 将该 gap 的 front / rear 车辆加入 `uncontrollable_vehicles_round`

这里的“最终占用的 gap”包括三类：

1. control-zone 新选中的 `gap_best`
2. merge-zone 中一旦已经形成并继续保留的 `locked_gap`
3. `merging` 状态下继续执行的 `locked_gap`

### 5.2 EffectiveControllable 的正式判断

正式判断必须始终使用：

1. `BaseControllable(vehicle)`：车辆本体是否可控
2. `vehicle ∉ uncontrollable_vehicles_round`：本轮是否仍允许把它当成可协同边界车

也就是说：

1. 一辆车即便在车辆类型层面是可控的，只要本轮已经进入 `uncontrollable_vehicles_round`，就必须按不可控处理。

### 5.3 四类分支的正式含义

#### 分支 A：front controllable + rear controllable

1. 按正常 OneStep 链路求解。
2. 正常计算 `delta_f_bar`、`delta_r_bar`、`delta_f_star`、`delta_r_star`、`d_i`、`t_m`、`p_m`、`J`。

#### 分支 B：front controllable + rear uncontrollable

1. 强制 `delta_r_bar = 0`。
2. `delta_f_bar` 正常计算。
3. 只有前车承担可调整量。
4. 若单侧容量不足以弥补缺口，则该 gap 不从候选表里消失，而是保留并直接赋极大分：
   `J = 10000`。
5. 若单侧容量足够，则继续完整求解并导出中间量。

#### 分支 C：rear controllable + front uncontrollable

1. 强制 `delta_f_bar = 0`。
2. `delta_r_bar` 正常计算。
3. 只有后车承担可调整量。
4. 若单侧容量不足以弥补缺口，则该 gap 不从候选表里消失，而是保留并直接赋极大分：
   `J = 10000`。
5. 若单侧容量足够，则继续完整求解并导出中间量。

#### 分支 D：front uncontrollable + rear uncontrollable

1. 强制 `delta_f_bar = 0`
2. 强制 `delta_r_bar = 0`
3. 若当前 gap 长度大于 `95m`，则允许其作为保底候选参与评分。
4. 这时强制 `delta_f_star = 0`、`delta_r_star = 0`。
5. 协同代价退化为 0，只保留 ego displacement / timing 相关代价。
6. 若当前 gap 长度不大于 `95m`，则保留该 row，但直接赋极大分：
   `J = 10000`。

### 5.4 关于 `delta_f_bar / delta_r_bar` 的最终理解

这一点必须写死，否则后面最容易被写成两层语义：

1. `delta_f_bar / delta_r_bar` 是“该侧边界车在当前 round、当前 gap、当前 controllability 条件下仍可被用于协同调整的容量上限”。
2. 单侧不可控时，不是把这侧“尽量算小一点”，而是直接置 0。
3. 双侧不可控时，两侧都直接置 0。

因此：

1. 单侧不可控是 score 分支层面的正式语义，不是 bundle 生成后的补丁。
2. 这件事必须发生在 gap 评分链路里，而不是在 bundle 落地以后再做“事后修正”。

## 6. runtime 状态、bundle 语义与运动状态机

### 6.1 runtime 状态的正式层次

最终实现中的正式 runtime 语义已经收口为“正式对象层 + round 上下文层”两层：

1. 跨帧持久的正式对象层
2. 单次 trigger round 的瞬时上下文层

正式对象层至少应包含：

1. `MVPlanState`
2. `GapPlan`
3. `Stage2Bundle`
4. `LateralTrajectory`

其中 `MVPlanState` 至少应有：

1. `zone_state`
2. `merge_state`
3. `current_plan_gap`
4. `locked_gap`
5. `active_bundle`
6. `active_lateral_trajectory`
7. `last_plan_step`
8. `last_plan_t`

当前代码里用的是：

1. `active_bundle_id`
2. `onestep_plan_bundles`
3. `controlled_vehicle_states`

这套“ID + 对象表”的实现形态可以继续保留，但它表达的正式语义必须等价于：

1. MV 当前是否持有一个有效 `active_bundle`
2. 该 bundle 控制哪些车辆
3. 该 bundle 对应哪个 `current_plan_gap`
4. 该 MV 当前是否持有一个有效 `active_lateral_trajectory`

实现层也允许使用 `current_plan_id / locked_plan_id / active_bundle_id / active_lateral_trajectory_id` 存储。
但这些 id 只是 registry key，必须解析到正式对象 `GapPlan / Stage2Bundle / LateralTrajectory`。
`current_plan_gap / locked_gap` 永远不能退化成裸 gap id。

单次 trigger round 的瞬时上下文则应明确只存在于这一轮内部：

1. `selected_gaps_round`
2. `uncontrollable_vehicles_round`
3. `tail_frontier_gap_index`
4. 本轮冻结的 gap snapshot

这些东西不应被误当成长期 runtime 记忆。
它们从 round start 以空壳或初值形式创建，再按 MV 顺序增量推进。

### 6.2 current_plan_gap、locked_gap、active_bundle 的关系

三者关系已经固定：

1. `current_plan_gap`
   表示控制区内最近一次规划得到、且仍被当前 MV 持有的 `GapPlan` 引用。
2. `active_bundle`
   表示当前 MV 的有效纵向协同控制计划。
3. `locked_gap`
   表示 MV 进入 `merge_zone` 后锁定的 `GapPlan` 引用，一旦锁定，合流区内原则上不再重选。

它们的生命周期关系是：

1. control-zone 触发重规划时，允许用新 `bundle` 替换旧 `bundle`，并同步更新 `current_plan_gap`。
2. MV 进入 `merge_zone` 时，若 `locked_gap` 为空且 `current_plan_gap` 不为空，则应立即把 `current_plan_gap` 锁成 `locked_gap`。
3. 合流区里若纵向条件未满足，则：
   `locked_gap`、`current_plan_gap`、`active_bundle` 全部保留，不得偷偷清掉。
4. 横向一启动后，原 `active_bundle` 立即 release，`MV.active_bundle` 清空；front / rear 退出纵向 bundle 的协同控制。
5. 横向完成后进入 `merge_completed`，下一轮 `step0` 再正式主线化，并清理 `current_plan_gap`、`locked_gap`、`active_lateral_trajectory`。

### 6.3 bundle 控制对象的正式规则

bundle 的边界身份永远保留 `front/rear` 语义。

不同分支下的 bundle 控制对象已经固定：

1. 双侧可控：
   bundle 控制 `MV + front + rear`
2. 仅前车可控：
   bundle 控制 `MV + front`
3. 仅后车可控：
   bundle 控制 `MV + rear`
4. 双侧不可控：
   bundle 只控制 `MV`

这条规则的意义是：

1. boundary identity 仍然保留 front / rear
2. 但实际进入受控集合的车辆，会随 controllability 分支变化

因此，后续实现里不应该再出现“gap 仍然指向 front/rear 两辆边界车，但 bundle 仍然默认三车全控”的隐式旧语义。

默认主线运动只作用于不在任何有效 `bundle.controlled_vehicle_ids` 中的主线车辆；
bundle 内主线边界车按 bundle 执行。

### 6.4 非触发帧与触发帧必须严格分离

这是 runtime 语义层必须守住的边界：

1. 非触发帧不能重新识别 gap。
2. 非触发帧不能重新打分。
3. 非触发帧不能偷跑新的 OneStep。
4. 非触发帧只能做三件事：
   继续横向轨迹、继续已有 bundle、默认运动。

### 6.5 merge lifecycle 的正式状态机

最终状态机已经收口为：

1. `normal`
2. `merging`
3. `merge_completed`

它们的含义是：

1. `normal`
   尚未开始执行横向合流；控制区内可重规划；合流区内可持有 `locked_gap` 并等待纵向条件满足。
2. `merging`
   已经启动横向轨迹；不再重选 gap；不再替换 bundle；只继续横向直到完成。
3. `merge_completed`
   横向已经完成，但该车尚未在本帧立即变成主线车；等待下一轮 `step0` 正式变性。

正式时序如下：

1. control-zone：
   可重规划，可替换 bundle，但不得启动实际横向合流。
2. merge-zone 且未 `merging`：
   先锁 gap，再用当前真实状态判纵向条件。
3. 纵向条件满足时：
   触发横向轨迹，`merge_state = merging`。
4. 横向一启动：
   原 `active_bundle` 立即 release，`MV.active_bundle` 清空；front / rear 退出纵向 bundle 的协同控制，回到默认主线运动或其所属的其他有效 bundle。
5. `abs(y_mv - lane_2_centerline) <= 0.1` 时：
   `merge_state = merge_completed`。
6. 下一轮 `step0`：
   把该车变性为主线车，并清理匝道 MV 运行时状态。

## 7. 场景层判断与 S07 验证口径

### 7.1 场景载体的选择

这轮验证不要求去构造一个“教科书式原始 S07 重放器”，
而是以项目里已经适配好的近似 S07 rolling 场景作为载体，
新增一个独立的 2-MV 正式场景入口。

换句话说：

1. 它不是历史 `one_step_algorithm` 意义上的原始静态 S07。
2. 但它已经是当前项目里最合适的 S07 近似桥接场景。
3. 后续多 MV 连续时间滚动验证，直接在这个载体上通过独立 2-MV 入口推进。

### 7.2 独立 2-MV S07 场景的第二辆 MV 放置口径

对 S07 验证场景的新增拍板是：

1. 在匝道上再放一辆 MV。
2. 新增位置按局部语义记为 `x_local = -60`。

结合当前近似 S07 rolling-entry 场景的桥接方式：

1. 现有 rolling-entry 主 MV 在 local frame 里是 `x_local = 0`。
2. 当前配置下它对应的 `x_global = 6600`。
3. 因而新增第二辆 MV 若按 `x_local = -60` 放置，则其对应的 bridge 全局位置可写成：
   `x_global = 6540`。

这里真正要固定的是相对位置关系，而不是执着于某个旧场景编号：

1. 原有 MV 是前车。
2. 新增 `x_local = -60` 的 MV 是后车。
3. 按本记录的多 MV 顺序规则，前车先处理，后车后处理。
4. 该独立 2-MV S07 rolling 场景已作为标准验证载体写入标准正文。

### 7.3 这个双 MV S07 载体要验证什么

这个场景暂时主要用于验证下面几类语义，而不是追求一次性覆盖所有未来随机流量问题：

1. 多 MV 连续时间滚动触发。
2. 前车先处理、后车后处理的 round 语义。
3. `selected_gaps_round` 的 frontier 收缩是否正确。
4. `uncontrollable_vehicles_round` 是否正确传播到后车。
5. 相邻 gap 共存时，后一辆 MV 是否正确落入单侧不可控或双侧不可控分支。
6. bundle 生命周期是否稳定。
7. `locked_gap -> merging -> merge_completed -> step0 主线化` 是否能在滚动场景里顺利跑通。

要特别避免的误区：

1. 不要把第二辆 MV 设计成一个带特殊逻辑的“测试替身”。
2. 它就应该是一辆普通的后方 MV，让算法自然处理它。

## 8. summary、事件与产物层判断

### 8.1 正式验收口径不再围绕旧 label

以后 summary / validation / tests 的正式口径应围绕结构和数值，不再围绕旧 `gap4` 之类的标签。

正式优先级如下：

1. `front_vehicle_id`
2. `rear_vehicle_id`
3. gap interval
4. `delta_f_star`
5. `delta_r_star`
6. `d_i`
7. `t_m`
8. `p_m`
9. `J`

### 8.2 gap_rows 必须成为正式中间产物

后续实现里，gap 评分不能只留下最终 `best_gap`，必须导出足够完整的 gap row 信息。

至少要能稳定导出：

1. gap identity
2. front / rear vehicle id
3. 是否可达
4. controllability branch
5. `delta_f_bar`

7. `delta_f_star`

这不仅为了 debug，也为了后续把断言从旧 label 迁移到结构化数值上。

`gap_rows` 不单独成为第六个顶层 summary 层；它归入 `mv_summaries / artifact_paths`。

### 8.3 summary 的正式顶层结构

当前 stage2 的 summary 主要还是单 MV 视角。后续正式顶层结构统一为：

1. `scenario_summary`
2. `round_summaries`
3. `mv_summaries`
4. `cross_mv_summary`
5. `artifact_paths`

其中 round 级至少应能回答：

1. 本轮为什么触发
2. 本轮冻结的 gap snapshot 是什么
3. 本轮初始 `danger` 集合是什么
4. 本轮 `selected_gaps_round` 的推进过程是什么
5. 本轮 `uncontrollable_vehicles_round` 的推进过程是什么
6. 本轮最后沿 frontier 如何变化

MV 级至少应能回答：

1. 该 MV 在本轮属于哪一种情况：
   `merging / merge_zone / control_zone / outside_control_zone`
2. 它看到的候选 gap 列表是什么
3. 它因 frontier 约束被删掉了哪些 gap
4. 它对每个候选 gap 落入了哪类 controllability 分支
5. 它最终选中了哪个 gap
6. 它生成了哪种 bundle
7. 它后续何时锁 gap、何时启动 merging、何时完成横向、何时 step0 主线化

### 8.4 事件导出的正式方向

后续事件层不做复杂事件系统，只导出最小正式事件集：

1. `trigger_round`
2. `gap_evaluation`

4. `bundle_released`
5. `current_plan_updated`
6. `locked_gap_created`
7. `lateral_started`
8. `lateral_completed`

### 8.5 现有 stage2 产物链的取舍判断

当前 stage2 runner / analysis / plot 链路不是废物，应尽量复用“输出通道”，但必须替换“输出语义”。

应保留的：

1. rolling runner 入口
2. history / event / trajectory 记录链
3. summary / report / plot 产出机制

必须替换的：

1. 单 MV 默认视角
2. 旧 gap label 真值断言
3. 只围绕纵向完成清 bundle 的阶段性叙事

替换后的正式 summary 视角应统一为：

```text
scenario_summary
round_summaries
mv_summaries
cross_mv_summary
artifact_paths
```

## 9. 最终实现轮廓判断

当前对最终实现轮廓的判断已经足够稳定，可以直接作为后续执行的骨架：

1. 保留 `RampMergeEngine` 这一层共用执行外壳。
2. 不修 legacy 分支，不再为它增加任何长期语义负担。
3. 把当前单 MV `onestep_stage2` 触发规划，改造成正式的 multi-MV round planner。
4. 把 gap 正式编号、四类 controllability 分支、95m 保底规则、gap_rows 中间量和 best gap 选择逻辑沉到 `onestep_kernel`。
5. motion 从“bundle 纵向执行到完成即清空”演化为完整 lifecycle：
   control-zone bundle 执行、merge-zone locked gap 保留、纵向条件判断、横向启动、merge_completed、step0 主线化。
6. runner / validation / tests 改成新标准口径。
7. 场景桥接层在当前实现阶段统一经 `ramp_merge_onestep_scenarios.py` 进入 `ramp_merge`。

从代码组织角度看，我的判断是：

1. `onestep_kernel`
   应承担正式的 gap 评估、四类分支、评分和中间量导出职责。
2. `planner`
   应承担 trigger round 组织、多 MV 顺序、frontier 约束、bundle 生成和 runtime 写回职责。
3. `motion`
   应承担 bundle 推进、默认运动、横向执行、LateralTrajectory 执行、完成判定和状态迁移职责。
4. `runner / analysis / validation`
   应承担新语义下的 summary、产物导出和测试验收职责。
5. `ramp_merge_onestep_scenarios.py`
   只提供 OneStep S05 / S07 / 2-MV S07 的 case spec 和初始场景桥接，不承载算法语义。

这里还要补一个实现层判断：

1. 多 MV 的 runtime 写回不得继续沿用“处理一辆，立刻把它写回 runtime，然后下一辆再继续读半更新状态”的单 MV 旧写法。
2. 正式方向固定为：一个 trigger round 内的计划结果先形成 `round_update`，再统一写回 runtime。
3. 这样更容易避免多 MV 同轮更新时出现半成品状态和覆盖问题。
4. 这里的 `round_update` 主要针对持久 runtime 写回；
   round context 的逻辑推进仍然发生在 planner 内部按 MV 顺序处理的过程中，
   不影响 frontier / uncontrollable 的轮内顺序语义。
