总方案
我建议未来项目只认一个正式场景概念：SceneSpec，也就是车表式场景定义。
你以后设计场景时，核心只需要描述：
scene(
    id="CUSTOM-2MV-6ML",
    vehicles=[
        mv("MV_A", x=6600.0, v=20.0),
        mv("MV_B", x=6540.0, v=18.0),
        lane2("ML_01", x=6480.0, v=20.0),
        lane2("ML_02", x=6560.0, v=22.0),
        lane2("ML_03", x=6660.0, v=20.0),
        lane2("ML_04", x=6790.0, v=19.0),
    ],
)
这就是唯一的人类维护入口。
不再让你关心 BASIC、ROLLING BASIC、S07、2MV S07、MVS built-in 各自怎么 build。那些都应该变成这个接口下面的数据实例。
统一接口分三层
第一层是人看的：SceneSpec。
它负责表达“这个场景里有哪些车”。每辆车有 id / lane / role / x / y / v / a / state / type / optional specs。常用 helper 自动补默认值：
mv(...)       -> on_ramp + on_ramp_mv + y=-3.5 + merge_state=not_started
lane2(...)    -> lane_2 + mainline + y=0.0 + merge_state=none
lane1(...)    -> lane_1 + mainline + y=3.5 + merge_state=none
第二层是机器看的：现有 ScenarioConfig。
这个不要废掉，反而要作为底层统一格式继续使用。现在 cormc/mvs/loader.py (line 14) 已经定义了场景字段，initial_vehicles 已经能表达多 MV、多主线车、不同速度、不同车道。未来 SceneSpec 应该编译成这个现有格式，再交给 load_scenario_config(...) 校验。
第三层是运行时输入：ResolvedScene。
静态场景只需要 ScenarioConfig。带边界生成/随机生成的场景，还需要额外携带 boundary_queue 或 arrival_profile，因为现有 ScenarioConfig 里并没有完整存随机队列的正式字段。也就是说：
SceneSpec
  -> ScenarioConfig              静态初始车辆
  -> optional BoundaryInputs     边界/随机生成输入
怎么利用现有底层
现有底层其实已经可以吃“车表”。不要重写这部分。
SceneSpec 编译出来的 ScenarioConfig 继续走现有链路：
load_scenario_config
  -> build_prefreeze_workspace_from_scenario
  -> freeze_simulation_state
  -> initialize_runtime_state
关键事实是：initialize_runtime_state 会自动把 physical_lane="on_ramp" 或 road_role="on_ramp_mv" 的车登记成 MV。也就是说 MV 数量天然可变，不需要每个场景写特殊算法。
主线 gap 现在主要来自 lane_2 车辆，所以“可合流 gap 的主线车”应该先放 lane_2。lane_1 可以作为环境车存在，但除非后面扩展 gap 识别，否则它不是 one-step 目标 gap 边界。
静态场景逻辑
静态确定性场景是第一优先级，也应该是接口的主路径。
默认规则：
boundary_generation_enabled = False
random_arrival_enabled = False
random_vehicle_attributes_enabled = False
ordinary_mainline_lane_change_enabled = False
platoon_cmc_enabled = False
mpc_lateral_tracking_enabled = False
原因很简单：你手摆了几辆车，就应该只跑这几辆车，不要中途冒出别的车干扰验证。
S07 2MV、未来 S02-S12 2MV、自定义多 MV、多主线车场景，都应该先走这个静态路径。
边界生成和随机生成怎么放
这里要分清楚两个概念。
边界生成是算法流程里的 step1。文档里写的“step1. 边界车辆生成钩子”代码里已经有实现：step1_prefreeze_boundary_generation_hook(...) 会在冻结状态前，把允许进场的新车放进工作区，并发出 boundary_generation 事件。
随机生成不是 step1 本身。随机生成是 step1 的上游。它负责提前生成一个“入口队列”：某辆车应该在什么时间、从哪个入口、以什么速度进来。然后每一步用当前状态判断能不能安全进场。
所以统一方案里应该这样建模：
静态车辆表：一开始就在场景里的车
边界入口流：未来可能进入场景的车
随机策略：如何生成入口流的到达时间、车型、速度等
step1：每一步把满足条件的入口车加入当前工作区
当前代码里，这条链路部分已经存在。random_generation.py 能生成 BoundaryQueueItem，compute_spawn_decisions(...) 能判断安全进场，step1_prefreeze_boundary_generation_hook(...) 能真正插车。完整 CormcEngine 也已经能接 random_queue。
但 one-step stage2 专用 runner 目前主要跑静态 catalogue，还没有把随机队列作为正式场景输入接进去。所以我的建议是：统一接口第一版先稳定静态场景；边界/随机作为 SceneSpec 的第二层能力设计进去，但实现时分阶段打开。
迁移思路
迁移目标不是“把旧代码搬到新地方”，而是把旧场景还原成统一车表。
迁移对象分三类：
BASIC / ROLLING BASIC：
  把现有 _mv/_lane2/_lane1_blocker 生成的数据改成 SceneSpec 车辆表。

ONESTEP S05/S07/S07-2MV：
  把 OneStepRampMergeCaseSpec 的 x_targets、MV 位置、lane2 车辆直接转成 SceneSpec。
  S07-2MV 不再需要专用 _build_s07_2mv_rolling_config，只是多放一辆 mv。

MVS built-in：
  车辆表也迁移到 SceneSpec；复杂的 expected_events、preloaded_assignments、notes 等作为 SceneSpec 的高级元数据保留。
之前的数据正好可以做迁移验证：同一个旧 scenario id，用旧 builder 生成的 ScenarioConfig，和新 SceneSpec 编译出的 ScenarioConfig，在车辆 ID、位置、速度、车道、role、module_overrides 上应该一致。对于 S07 2MV，还可以继续用现有 lifecycle/cross-MV 测试验证行为没变。
旧 builder 删除原则
我建议“快速硬切”，但不是盲删。
迁移完成后的最终状态应该是：
保留：
  一个 SceneSpec 定义层
  一个 registry
  一个 compile_to_scenario_config
  一个统一 loader/run 入口

删除：
  basic_scenarios.py 里的重复 vehicle helper / base_config
  rolling_basic_scenarios.py 里的重复 vehicle helper / base_config
  ramp_merge_onestep_scenarios.py 里的 S07 专用 2MV builder
  mvs/loader.py 里大量手写内置场景构造逻辑
旧的场景 ID 可以保留，方便报告和测试对齐；但旧的“生成方式”不保留。
也就是说，BASIC-01 这个名字可以继续存在，但它应该从统一 registry 里加载，而不是从 basic_scenarios.py 的专用 builder 里加载。
我建议的最终心智模型
以后你造场景时，只问三个问题：
1. 初始时路上有哪些车？
2. 未来边界入口还会不会来车？
3. 这个场景要验证什么现象？
第 1 个问题用 vehicles=[...] 表达。
第 2 个问题用可选 boundary_sources=[...] 表达。
第 3 个问题用 expectations / tags / notes 表达。
算法入口不再关心这个场景来自 BASIC、S07、随机 6450，还是你手写的新实验。它只拿统一编译后的场景运行。
我的默认建议是：**先把“静态确定性多 MV、多主线车”做成唯一正式接口；同时在接口设计里预留 boundary/random 层，但不把随机和静态混在同一个简化车表里。**这样结构干净，也和文档 step1 的真实算法位置对齐。
