设计目的：

## 场景 S05：密集交通，部分 gap 协作不可行

```text
X = [-100, -50, 0, 50, 100, 160, 240]
```

预期：

```text
best_gap ≈ [-100, -50]
中间多个 gap 应该 coop_feasible = False
```

设计目的：

验证协作可行性筛选：

$$

\bar\delta_f+\bar\delta_r \geq \Delta

$$

如果不满足，就必须剔除。文档中也明确说，如果最大可调整量之和小于缺口，该 gap 不可行。fileciteturn5file1

重点验证：

```text
[-50,0], [0,50], [50,100] 这类密集 gap 不应强行评分
coop infeasible 的 gap 不应参与 best_gap 选择
```

## 场景 S11：协作代价权重 $w_c$ 敏感性测试

```text
X = [-120, -40, 20, 90, 180, 270]
```

默认参数预期：

```text
w_c = 0.2 时，best_gap ≈ [20, 90]
```

建议参数扫描：

```text
w_c = 0       预期偏向近处、高协作 gap，例如 [-40,20]
w_c = 0.2     预期选择折中 gap，例如 [20,90]
w_c = 1 或更大 预期偏向低协作 / 无协作 gap，例如 [-120,-40]
```

设计目的：

验证 $w_c$ 是否真的控制“协作代价”的重要程度。

重点观察：

```text
w_c 越大，算法越不愿意让目标车道车辆调整
w_c 越小，算法越愿意选择离合流车更近但协作量更大的 gap
```

## 场景 S12：完全对称 tie-breaking 测试

```text
X = [-85, 0, 85]
```

两个 gap：

```text
[-85,0]
[0,85]
```

二者长度都为：

```text
85m
```

中心分别为：

```text
-42.5m
+42.5m
```

预期：

```text
两个 gap 的评分应非常接近，理论上可以完全相等
```

设计目的：

验证程序在分数相等或几乎相等时的处理方式。

重点建议：

你需要在代码里明确 tie-breaking 规则，比如：

```text
规则 A：选择 index 最小的 gap
规则 B：选择 |d_i| 更小的 gap
规则 C：返回所有并列最优 gap
```

这个场景不一定要求某一个固定 gap 被选中，但必须要求程序行为可解释、可复现。

## 场景 S13：$q$ 参数敏感性测试

```text
X = [-180, -90, -25, 30, 110, 190, 250]
```

这是原始场景，但专门用来扫 $q$。

建议扫描：

```text
q = 0.5
q = 1
q = 2
q = 4
q = 6
q = 10
```

预期趋势：

```text
q 较小时，前后车调整更平均，空间偏好弱
q 较大时，算法强烈偏向可调整空间更大的方向
q = 6 时，[30,110] 应该保持为最优 gap
```

设计目的：

验证空间敏感权重：

$$

\gamma=\left(\frac{\delta_{ref}}{\bar\delta}\right)^q

$$

是否生效。

重点观察：

```text
[30,110] 的 delta_f / delta_r 随 q 的变化
best_gap 是否随 q 改变
C_coop 是否出现过大值
```

# 四、建议最终做成测试文件的格式

你可以把每个场景整理成类似这种结构：

```text
{
  "id": "S06_equal_split",
  "x_targets": [-100, -20, 45, 125, 210, 300],
  "expected": {
    "best_gap": [-20, 45],
    "delta_f": 10.0,
    "delta_r": 10.0
  },
  "purpose": "验证左右可调整空间相等时，协作调整量是否平均分配"
}
```

对参数扫描场景可以写成：

```text
{
  "id": "S11_wc_sensitivity",
  "x_targets": [-120, -40, 20, 90, 180, 270],
  "sweep": {
    "w_c": [0, 0.2, 1.0]
  },
  "expected_trend": "w_c 越大，越倾向低协作代价 gap"
}
```

我的建议是：**普通场景用固定 expected，参数敏感性场景用 expected trend，不要强行写死所有参数扫描下的最优 gap。**这样后面改公式或改权重时，测试不会过度脆弱。
