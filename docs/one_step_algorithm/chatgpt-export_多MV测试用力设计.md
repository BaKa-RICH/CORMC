# 多 MV 滚动优化测试用例设计与代表场景数值验证

## 0. 文档定位

这份文档是在原单 MV 测试用例基础上的泛化版本，目标不是重新发明一套多车公式，而是验证你最新实现中的 rolling 机制是否能够把单帧 kernel 反复、稳定、可解释地用于 2MV、3MV、4MV 场景。

原单帧算法的核心流程仍保持为：

```text
可达 gap 筛选 → 候选合流点 → 协作调整量 → 评分 → 选最优 gap → 只对最优 gap 生成轨迹
```

多 MV 测试要验证的是：每辆 MV 被触发时，算法能用当前目标车道状态重新构造 gap；上一辆 MV 的合流结果会改变下一辆 MV 的候选 gap、容量和评分。

## 1. 我对这次需求的理解

你要的不是“把一个单 MV 场景复制几遍”，而是要设计能够真正压测 rolling 泛化能力的测试用例。也就是说，测试用例必须覆盖以下几类问题：

1. 多辆 MV 是否都能被求解，而不是只处理第一辆；
2. 第一辆 MV 合流后，是否会作为目标车道车辆参与下一次 gap 构造；
3. 连续合流是否会消耗相邻 gap 的可调整容量；
4. 多辆 MV 争夺同一局部区域时，后续 MV 是否能重新选择其他 gap；
5. 对不可达、协作不可行、单侧不可控、边界 gap、tie-breaking、参数敏感性等工程分支是否仍然稳定。


因此本文件把测试设计分成 2MV、3MV、4MV 三组，共 21 个场景，不超过 25 个。每个场景给出 `x_targets`、`x_m_list`、预期 rolling 序列、设计目的与重点验证模块。


## 2. 默认测试协议

除场景单独说明外，全部用以下默认参数：

```text
x_m_list 按给定顺序触发：MV1 → MV2 → MV3 → MV4
v_ref = 20

boundary_adjustment = 100
time_mode = strict，即 t_m = max(t0, ta, tv)
```

每一步 rolling 的静态验证更新规则如下：

```text
1. 用当前 X_current 和当前 MV 的 x_m0 调用单帧 kernel。
2. 若无 reachable / feasible gap，则该 MV 记录 no_feasible_gap，X_current 不更新。
3. 若求得 best_gap = [x_r, x_f]：
   x_r' = x_r - delta_r
   x_f' = x_f + delta_f
   x_mv_insert = x_m0 + d
4. 将 x_mv_insert 插入目标车道车辆集合，并重新排序，作为下一辆 MV 的 X_current。
```

这个更新是用于测试设计的“相对位置验证口径”。真实仿真中车辆会按时间推进，但只要所有目标车道车辆参考速度相同，静态相对位置更新足以验证 rolling 的 gap 构造、容量消耗和选择逻辑。


每个场景建议至少记录：`G_i, c_i, D_i, reachable, coop_feasible, Delta, delta_f_bar, delta_r_bar, gamma_f, gamma_r, delta_f_star, delta_r_star, d_i, t_m, p_m, C_coop, C_ego, J, best_gap, failure_reason`。

## 7. 推荐断言清单

| 断言编号 | 断言内容 |
| --- | --- |
| A01 | 每个 MV 触发后必须记录 best_gap 或 no_feasible_gap，不允许静默跳过。 |
| A02 | reachable=False 的 gap 不得进入最终评分集合。 |
| A03 | coop_feasible=False 的 gap 可记录诊断行，但不得成为 best_gap。 |
| A04 | 若 Delta=0，则 delta_f=0 且 delta_r=0。 |
| A05 | 若某侧不可控，则该侧容量置为 0，对应 delta 必须为 0。 |
| A06 | 每次成功合流后，x_m0+d 必须插入下一步 X_current。 |
| A07 | 更新后目标车道位置必须重新排序，并允许已合流 MV 作为后续 gap 边界车辆。 |
| A08 | 选中 gap 更新后的长度必须满足 G_req=85。 |
| A09 | strict 模式下，t_m 必须满足速度约束下界 tv。 |
| A10 | tie 场景必须按固定规则返回，建议 index 最小或返回并列集合。 |
